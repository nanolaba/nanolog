# AGENTS.md

Guidance for coding agents (Claude Code, Codex, Copilot and others) working in this repository. `CLAUDE.md` only points here.

## Build & Test

Maven project targeting **Java 8** (`maven.compiler.release=8`). Do not introduce Java 9+ APIs in `src/main`. Tests may rely on a JDK (not a JRE): `LOGTest` compiles a class at runtime with `javax.tools.ToolProvider`.

- Full build: `mvn verify -Dgpg.skip=true` (the default `verify` tries to GPG-sign artifacts)
- Tests + mutation analysis: `mvn test`
- Single test class: `mvn test -Dtest=LOGTest`
- Single test method: `mvn test -Dtest=LOGTest#methodName`
- Compile only (also regenerates the README files): `mvn compile`
- Fast JUnit-only loop while developing: `mvn test-compile surefire:test -Dtest=LOGTest`
- The module descriptor: `src/main/java9/module-info.java` is compiled with release 9 into `META-INF/versions/9` of a multi-release jar by the `java9-module` profile, active from JDK 9 on (javac 8 cannot compile it); every other class stays Java 8 bytecode. A jar built on JDK 8 has only `Automatic-Module-Name`, so release builds run on JDK 11 or newer. The module requires only `java.base`, with `requires static` for SLF4J and JUnit and no `provides` for the services of JUnit (a module that provides a service of an absent module does not resolve). Keep it so: do not reference a class outside `java.base` directly (`RunLog.pid` reads `java.management` through reflection), or a `jlink` image of `java.base` alone fails. `sh src/it/jlink/run.sh` after `mvn package` on JDK 11+ builds such an image with a tiny module that logs once, as CI does on JDK 11, 17 and 21.
- The calls from Kotlin (the `kotlin` profile compiles `src/test/kotlin` with kotlin-maven-plugin, test scope only): `mvn -P kotlin test-compile surefire:test -Dtest=KotlinCallersTest`, on JDK 17 as in CI. The profile moves `testOutputDirectory` to `target/kotlin-test-classes` (kotlin-maven-plugin has no output of its own for tests), so a build without it, pitest included, never meets the Kotlin classes without the Kotlin library. `KotlinCallers.kt` holds every call shape as Kotlin writes it; add the shapes of a new API there. A new overload must keep it compiling: Kotlin reports an overload resolution ambiguity that Java does not, for `(String, Object...)` next to `(String, Supplier<?>...)` (checked once by adding that overload). `LOG.lazy` stays a wrapper value for this reason. A bare Kotlin block given to `LOG.timed(name, ...)` or `LOG.unit(name, ...)` takes the `Runnable` overload; the value-returning one needs `Supplier { ... }`.
- The tests against SLF4J 1.7 (the `slf4j-1.7` profile sets `slf4j.version` to 1.7.36 and skips the README generation, since the README names the version of the main build): `mvn -P slf4j-1.7 clean test-compile surefire:test`. `Slf4jLogger` must keep to the API of 1.7; compiling under the profile fails on anything newer.

CI (`.github/workflows/ci.yml`) runs `mvn -Dgpg.skip=true -Dcheck=true verify` on JDK 8, 11, 17 and 21, and on JDK 8 the JUnit tests once more under the `slf4j-1.7` profile, and on JDK 17 the calls from Kotlin under the `kotlin` profile; on JDK 11, 17 and 21 it builds a `jlink` image with the jar (`src/it/jlink/run.sh`). Actions are pinned to commit SHAs and the token is read-only; keep it that way when editing the workflow.

A GraalVM native image and R8 need no setup from users: `src/main/resources/META-INF/native-image/com.nanolaba/nanolog` registers the no-argument constructors of the loggers that `nanolog.logger` may name (with `queryAllPublicMethods` for `LoggerIntrospection`), the methods of `StackWalker` that `CallerDetection.StackWalk` looks up, `Console.isTerminal` for `Colors` and the resource `nanolog.properties`; `META-INF/proguard/nanolog.pro` keeps the constructors of `*Logger`, `isEnabled` of every `ILogger` and the attributes `InnerClasses` and `EnclosingMethod` that `CallerDetection.topLevel` needs. A new reflective entry point, or a logger with a constructor for `nanolog.logger`, goes into both. The CI job `native` builds a native image with `src/it/native/run.sh` on GraalVM 21 and 25 and checks the output of `ConsoleLogger`, its settings read from a `nanolog.properties`, and of `JsonLogger`.

The OpenSSF Scorecard (`.github/workflows/scorecard.yml`, weekly and on every push to `main`) publishes the score shown by deps.dev and https://scorecard.dev/viewer/?uri=github.com/nanolaba/nanolog. Publishing restricts that workflow: no top-level env or write permissions, and its job uses only checkout, upload-artifact, upload-sarif and scorecard-action. CodeQL (`.github/workflows/codeql.yml`, on pushes and pull requests to `main` and weekly) analyses the Java sources and the workflows in build mode `none`, without Maven; its alerts and those of Scorecard are under Security → Code scanning. The OpenSSF Best Practices badge of the README comes from https://www.bestpractices.dev/projects/16916 (Metal series), whose answers describe the build, tests, CI, SECURITY.md and CodeQL: a change to any of them may need an edit there, which anyone with push access can make after signing in with GitHub. Dependabot (`.github/dependabot.yml`) proposes the updates of the action SHAs and of the Maven build weekly, without new majors of SLF4J and JUnit. The ruleset on `main` blocks force pushes and deleting the branch, and merges a pull request only with one approval and the required checks green: the four `JDK` jobs, both `GraalVM … native image` jobs and both `CodeQL` jobs, on a branch up to date with `main`. Repository and organization admins bypass it, so the maintainer's direct pushes stay allowed (GitHub reports the bypass); a renamed or new CI job needs its name changed in the ruleset too, or pull requests wait for a check that never comes. The Scorecard alert Code-Review is dismissed as won't fix: the maintainer's commits have no second reviewer.

### Javadoc

`maven-javadoc-plugin` runs with `doclint=all` and `failOnWarnings=true`, so every public and protected class, constructor, method, field and enum constant needs a Javadoc comment, with `@param` / `@return` tags and a first sentence before them (JDK 18+ rejects a tag-only comment as "no main description"). JDK 8 javadoc does not report missing comments at all, so check with a newer JDK as well, as CI does: `JAVA_HOME=<jdk17+> mvn javadoc:javadoc`. The plugin skips a run whose sources look unchanged: delete `target/maven-javadoc-plugin-stale-data.txt` (and `target/reports`) to force it. The level overloads of `LOG` share wording per signature shape; keep a new overload consistent with its siblings.

### Pitest mutation coverage (important)

The `test` phase is wired to run **pitest-maven** with `mutationThreshold=100`. Any surviving mutant fails the build, not just failing unit tests. When changing production code:

- `mvn test` covers both JUnit and mutation analysis; run it before every commit.
- If a mutant survives, add a test that would catch the mutation rather than weakening the threshold. "Mutations with no coverage" means a line is never executed by tests: cover it.
- Pitest's default mutators do not remove `synchronized` blocks, so thread-safety fixes need a deterministic test of the contract instead (see `ConsoleLoggerTest.testDateFormatIsGuardedByItsMonitor`).

## Architecture

Nanolog is a tiny SLF4J-compatible logging facade: a handful of source files in one package, no runtime dependencies. The whole public API is static methods on one class; there are no per-class logger fields.

### The single entry point: `LOG` (`src/main/java/com/nanolaba/logging/LOG.java`)

All logging goes through static methods on `LOG` (`LOG.info(...)`, `LOG.debug(...)`, ...). Each level has the same set of overloads: explicit source `Class`, `Throwable`, `Supplier<Object>` for lazy messages, `String` + `Object...` for parameterized messages, and since 1.1 the combinations `(Throwable, String, Object...)` and `(Class, Throwable, String, Object...)`. All overloads funnel into the private `LOG.doLog(...)`: overloads with an explicit `Class` through the public `LOG.log(level, class, throwable, supplier, args...)`, the others through `logFromCaller(...)`, which first asks the guarded `ILogger.mayBeEnabled(level)`, walks the stack only when it says `true`, and then passes the detected source class and caller frame. The no-argument `isXxxEnabled()` methods do the same through `isEnabledForCaller`, so a level that is off for every class costs no stack walk; `LevelCheckBeforeStackWalkTest` counts walks through `CountingLocator`. `doLog` checks `isEnabled` and hands a `LogEntry` to the configured `ILogger`. Both calls into the logger are guarded: a logger that throws is reported once per class through `LOG.reportLoggerFailure` (tests call `LOG.clearReportedLoggerFailures()`), a throwing `isEnabled` counts as enabled, and an entry the logger fails to write goes to the `LOG.Fallback` `ConsoleLogger`, which prints every level to `System.err`. The `isXxxEnabled()` methods go through the same guard. In strict mode (`nanolog.strict`, read by `LOG.init()`) `writeCall` first runs `checkCall`, which reports a template whose placeholders do not match its arguments, an argument equal to the message of the entry's exception (`checkExceptionMessage`) and a call site seen with another template than its first (`checkConstantTemplate`, which keeps the first template of each call site in `TEMPLATES` and names it in the text, so `System.err` reports a call site once). Only `doLog` and `LOG.Limited` go through `writeCall`; the lines of timers and units go straight to `write`, since a timer writes two templates (`took`, `failed after`) at one call site. Each finding prints a `[NANOLOG]` line as `nanolog.diagnostics` says, and is also handed, every occurrence, to `ILogger.onDiagnostic` (guarded: a throwing logger is reported through `reportLoggerFailure`), so `MemoryLogger.assertNoDiagnostics()` sees a template that an earlier test already printed. It must never throw or change the entry. Tests that enable it call `DefaultLoggerCreator.forgetDiagnostics()`. The fields `LOG.logger` and `LOG.strict` are `volatile`, so a logger installed while other threads log (`MemoryLogger.install()` in a test) is seen by them; `LOGTest` asserts the modifier because pitest does not mutate it. Keep any new field that every logging call reads `volatile` as well. When adding an overload, add it to all five levels and extend the per-level tests in `LOGTest`, which assert `LogEntry.toString()`.

Overload resolution matters: the `Object` and `Supplier` forms win in the non-varargs phases, the varargs forms only apply when extra arguments are present. Do not add overloads that make existing calls ambiguous (`LOG.info(e, "text")` must keep resolving to `(Throwable, Object)`).

### Rate limiting: `LOG.once()`, `LOG.atMostEvery(...)`

Both return a `LOG.Limited` view with four overloads per level. The view is nested in `LOG`, so caller detection skips its frames like those of `LOG`. `Limited.log` checks in this order: `mayBeEnabled`, caller detection, `isEnabled`, then `LOG.acquire(callSite, periodNanos)`, and only then resolves the message; a disabled call is never counted. `acquire` keys a `RateState` by the call site (`StackTraceElement`) in `LOG.LIMITS`, which needs no eviction because call sites are bounded by the code. `RateState` holds two `AtomicLong`s: a call gets through only by winning the compare-and-set of the last entry time, and every other call increments the skipped count, so each call is logged or counted exactly once (`RateLimitTest.testConcurrentCallsAreLoggedOrCountedExactlyOnce`). `once()` is a period of `Long.MAX_VALUE`; a period of zero or less, or a `null` unit, limits nothing and prints no diagnostic, because a loop would flood `System.err`. A call without a call site (`Caller.NONE`) is not limited. The clock is the package-private `LOG.nanoClock`, and `LOG.clearLimits()` forgets the state; tests replace and restore both. The skipped count reaches loggers as `LogEntry.getSkippedCount()`. Entries built by `Limited` carry `LOG.Limited` as their package-private `LogEntry.getCallerBoundary()`, which `Slf4jLogger` passes to location-aware backends instead of `LOG`: a boundary of `LOG` alone would make Logback and Log4j report the frame of `Limited` as the call site.

### Units of work: `LOG.unit(...)`, `Units`

A unit (`Units.Scope`, the implementation of the public interface `LOG.Unit`) is opened by `LOG.unit`, which detects the caller once, so the unit line has the class and call site of the `LOG.unit` call. `LOG.unit(failureLevel, name)` and its lambda forms set `Scope.failureLevel`, the level of the line for the outcomes `error` and `interrupted` (#104); `null` and the forms without a level, which call the ones with it, give `ERROR`, and `ok` is always `INFO`. `Units.open` makes it the open unit of the thread in `Contexts.State` next to the pairs of the context, so `LogEntry` reads both with one `ThreadLocal` read and `LOG.wrap` carries both. `LOG.write` calls `Scope.count` for the unit of each entry, which counts it in that unit and every parent; the line of a unit is created by `LogEntry.createUnitLine` without a unit, so a failed child does not count twice in its parent. `close()` calls `end()`, which calls `Contexts.leave` (the nearest open ancestor becomes current, so units closed out of order leave the thread clean) and `end(false)`, which ends the unit once (`AtomicBoolean`): the outcome, then sampling (`Units.sample`, `Units.slowNanos`, the seam `Units.random`), then a `Units.Ending` with the arguments as `LOG.kv` fields, the first three of them placed in `Units.TEMPLATE`, and the breadcrumbs of a failed unit, which `LOG.writeUnit` writes. The caller boundary of the line is `Scope.BOUNDARY` when the unit writes it itself (`close()`, `run`, `interrupt()`), and `bodyBoundary` (the skipped helper that called `LOG`, or `LOG`) when `LOG.unit(name, body)` writes it in `endUnit`: no frame of `Units` may be on the stack then, since a location-aware SLF4J backend takes the frame after the first run of frames of the boundary class (#102). Fields of `put` named like the ones the unit sets (`Units.RESERVED`) are ignored. `error.key` is `Units.key` of the template and call site of the first `ERROR` entry (`Summary.template` / `Summary.where`) or of the exception class and top frame for `fail`; `String.hashCode` keeps it the same between runs. Open units live in `Units.OPEN`; `Summary.printOnce` writes them as `interrupted`, innermost first, before the summary, and `Units.open` registers the summary hook so that this happens at exit even with the summary off. `Summary.template` names a unit line `unit <name>`, since every unit shares the template. Tests replace `LOG.nanoClock`, `Units.random` and `Summary.shutdownHooks`.

### Timers: `LOG.time(...)`, `Timers`

`LOG.time(level, name)` asks `mayBeEnabled` before anything else and `isEnabled` after caller detection, and returns `Timers.NOTHING`, which reads no clock, for a level that is off (or `null`). A `Timers.Timing` keeps the caller of the `LOG.time` call and the start from `LOG.nanoClock`; `stop()` lets its line be written once (`AtomicBoolean`), by `LOG.writeTimer`, which checks the level again and only then reads the clock in `fields()`, the `kv` fields `timer` and `duration_ms` (the field model of `Units`). `close()` writes it with `Timing.BOUNDARY` as the caller boundary for location-aware SLF4J backends. `LOG.timed` runs the body itself and writes the line in `endTimed`, with the exception (`{} failed after {} ms`) before throwing it on, and with `timedBoundary`: as for `LOG.unit(name, body)`, only frames of `LOG` may be between the call and the logger (#102). When a try-with-resources block closes a timer or a unit, the `LOG.time` or `LOG.unit` call is no longer on the stack and SLF4J cannot be given a call site, so such a backend shows the end of the block; README *Slf4jLogger* says so.

### Repeats: `nanolog.console.repeats`

With `collapse`, `ConsoleLogger.log` goes through `logCollapsing` under `repeatsLock`: an entry that `isRepeat` the last one written in full (level, `isDbg`, source class, caller, formatted message, skipped count, exception class and message, trailing fields and context; a comparison that throws is no repeat) is counted, any other entry first writes the count (`printRepeats`: `writeHead`, the line without the source line and the stack trace, plus `(repeated N more times in T)`, through `applyMultiline` and the colours) and is then written. A repeat more than `REPEATS_PERIOD_NANOS` after the start of the run writes the count so far and starts a new run; the clock is `LOG.nanoClock`. `flushRepeats` writes what is left and forgets the last entry: `LOG.init` calls it for the logger it replaces, and `Summary.printOnce` through `LOG.flushRepeats()` for the consoles of the installed logger, a `CompositeLogger` included; the first repeat registers that hook. `JsonLogger` overrides `collapsesRepeats` to `false`, and `RunLog` has a `log` of its own, so neither collapses.

### Source lines: `nanolog.console.showSourceLine`

`DbgSource.lineText` reads the trimmed line of a frame (cut at `MAX_LINE`) through the same `find` / `read` as the text of a `dbg` call, so it shares the source roots, the staleness check and the fallbacks; it has a cache of its own (`LINES`), which `clearCache` clears with the other and which stops growing at `maxCachedLines`, since an exception may carry made-up frames. For the same reason `DbgSource.read` takes only a plain file name from a frame (no `/` or `\`) and only a file that, normalized, lies inside its source root, so a forged frame cannot read a file outside the sources into the log. `ConsoleLogger.writeSourceLine` writes it after the context, on a line of its own, and ends that line too when a throwable follows; `addDelimiter` writes no space after a line break, so the exception starts its own line. `stackTraceOf` annotates the printed or shortened trace in `withSourceLines`: the first `MAX_SOURCE_FRAMES` frames outside the JDK (`Uncaught.isJdk`) whose class resolves and whose line is found, over the throwable and its causes (an identity set stops a cycle), matched to the printed lines by `StackTraceElement.toString()`, which is what both printers write after `at `; a failure keeps the trace as printed. `JsonLogger` puts the line into `"caller"` as `"source"`.

### Diagnostics: `printDiagnostic`, `printNotice`, `nanolog.diagnostics`

`DefaultLoggerCreator.printDiagnostic` prints a problem and applies `nanolog.diagnostics` (`Diagnostics.ONCE`, `ALL`, `OFF`; read at the start of `createDefaultLogger` and again after the keys of `nanolog.properties` are copied, so the file can set it before its own keys are reported): `once` remembers the text in `PRINTED`, at most `maxRemembered`, past which a new one is printed without being remembered. It returns whether it printed, so a stack trace that belongs to a diagnostic is printed only with it. `printNotice` prints what is not a problem (the run summary, the line of agent mode, the path of the run log, the `LOG.dbg` calls at exit) whatever the setting; `printNotices` prints several such lines with one `println`, which Surefire relays as one piece, so the summaries of two forks do not mix (#93). An invalid setting goes through `printInvalid`, which appends `origin`: the keys copied from the file are remembered in `FROM_FILE` with their value, so a system property set later with another value is told apart. Strict mode and `nanolog.dbg=fail` call `printDiagnostic` for every finding and leave the deduplication to it (the text names the call site); `ILogger.onDiagnostic` gets every finding. Logger failures and loggers without `ILevelControl` keep their once-per-class sets and print again under `all`. `AbstractLoggerTest` forgets the printed diagnostics before each test (`DefaultLoggerCreator.forgetDiagnostics()`), and `LOG.clearReportedLoggerFailures()` forgets them too.

### Catching: `LOG.catching(...)`, `Uncaught`

`LOG.catching` catches `Exception` (not `Error`) and logs through `logFromCaller`, so caller detection skips the frames of `LOG` and finds the code that called it; an `InterruptedException` sets the interrupt flag again. `LOG.installUncaughtExceptionHandler` installs an `Uncaught` unless the default handler already is one; `Uncaught.uncaughtException` calls `LOG.writeUncaught` inside a `try` that swallows everything and then the previous handler. `writeUncaught` delivers `Breadcrumbs.drainThread()` first (the error may be inside a unit, which would not drain the thread ring), logs through `doLog` with the class and frame of `Uncaught.origin` (the first frame outside the `java.`, `javax.`, `jdk.`, `sun.` and `com.sun.` packages, else the top frame; the class resolved by `CallerDetection.ThrowableWalk.resolveClass` and made top-level), and then `Units.interruptThread()` finishes the open units of the thread, innermost first. Tests set the default handler to `null` first and restore the original afterwards.

### java.util.logging: `JulLogger`, `NanologHandler`

`JulLogger` writes an entry to the JUL logger of its source class (held in a map, since JUL forgets the level of a logger that is collected) as a `LogRecord` with the formatted message, the skipped count, the trailing fields and the context, and always sets the source class and method, even to `null`, so JUL does not infer a frame of Nanolog as the caller. `NanologHandler.publish` resolves the source from `getSourceClassName()` (JUL infers it) or the logger name, finds the frame of the call on the current stack to have its line, formats the message with a `Formatter`'s `formatMessage` and calls `LOG.writeLine`, which `SystemStreams` uses too. A `ThreadLocal` marks a record on its way to Nanolog: one that comes back through `JulLogger` is a loop, reported once and dropped. `install()` swaps the handlers of the root logger and `uninstall()` restores them. There is no `System.LoggerFinder`: as a service it would take over `System.Logger` for every application with the jar; the default finder sends `System.Logger` to JUL, and `NanologHandlerTest` checks that path on Java 9+. The module descriptor `requires static java.logging`, so an image of `java.base` alone still works.

### Files: `FileLogger`

`FileLogger` extends `ConsoleLogger` for its levels and layout and overrides `log` to write the line (`createLogString`, or that of a `JsonLogger` created `quietly` for `json`) to the file in UTF-8, so repeats are never collapsed and there are no colours; `Agent.shorten` leaves it alone. The file opens on the first entry (the directory created, `append` applying to this first opening only; after `close()` it is appended to). In the `entry` mode the stream of `Files.newOutputStream` has no buffer, so each write reaches the file; `buffer` wraps it in a `BufferedOutputStream` and registers a flush at the exit through `FileLogger.shutdownHooks`, which tests replace. `rollOver` closes the file, deletes the last backup and moves the others up, then opens a new file; a line is never split, and one larger than `maxSize` on an empty file is written whole. An `IOException` while writing makes the logger write to `SystemStreams.err()` from then on, after one diagnostic; one while rolling over turns rollover off and appends. `LOG.flush()` calls `ILogger.flush()` (guarded by `reportLoggerFailure`), which `CompositeLogger` forwards. `FileLoggerTest` works in a `@TempDir` and closes every logger it opens, since Windows cannot delete an open file.

### System streams: `LOG.captureSystemStreams()`, `SystemStreams`

`SystemStreams.capture()` keeps `System.out` and `System.err` and installs print streams over `SystemStreams.Lines`, UTF-8 and without autoFlush (which would flush after every write and turn partial lines into entries). `Lines` collects bytes per thread until `\n` (a `\r` before it is dropped) or `flush()`, finds the printer with the `Throwable` walk past `java.io.`, `sun.nio.cs.`, `jdk.internal.`, `java.util.Formatter`, `java.lang.Throwable` and its own frames (`SystemStreams$`), falls back to the classes `SystemOut` / `SystemErr`, and writes through `LOG.writeLine`, past strict mode. Everything Nanolog prints itself goes through `SystemStreams.out()` / `err()`, the kept streams while capturing and `System.out` / `System.err`, read on every call, otherwise, so the tests that redirect the streams keep working: `ConsoleLogger.getOutputStream`, `LOG.Fallback`, `printDiagnostic`, `printNotice`, `NanologExtension`. Use them for any new output. The `LOGGING` thread local is set while `Lines` writes an entry and while `LOG.deliver` hands one to the logger (`enterLogging` / `leaveLogging`, only while capturing), and anything printed then passes through to the kept stream: no loop, also for a logger that prints. `restore()` puts back only a stream that is still the capturing one.

### Installing the logger: `LOG.init(...)`, `LOG.lock()`

`LOG.init(logger)` and `LOG.init()` find their caller through `LOG.Origin.ofCaller()`, which reads the frames of a `Throwable` (`CallerDetection.ThrowableWalk.stackTraceOf`) directly, not through `LOG.callerLocator`, so they never count as a walk of a logging call (`LevelCheckBeforeStackWalkTest`). It passes over the frames of Nanolog, of method handles (`isMachinery`) and of reflection (`isReflection`: `jdk.internal.reflect`, `java.lang.reflect`, `sun.reflect`), so a reflective `LOG.init` belongs to the code that made it (#91); the first other frame is the origin, and if `nanolog.caller.skip` names its class (`isSkipped`), a container that installs the logger for the application, the origin has a `null` organization, which `differ` never reports. `installedBy` keeps the `Origin` (call site and organization, the first two segments of the package) of a logger installed by `init(logger)`, and `null` for the logger of the configuration (the class initialiser runs `configure()`, `init()` runs it and resets the field) and for one of `MemoryLogger`. A replacement is reported when the previous origin is not `null`, its organization differs and the logger is another one; a call site is not enough, since applications and their tests install loggers from many places. `locked` (`LOG.lock()`, or `nanolog.logger.lock` read at the end of `configure()`) makes both `init` methods print `Logger locked: ...` and return. `MemoryLogger` goes through the package-private `LOG.install(logger, origin)`, past the lock and without a diagnostic, and restores the previous origin on `close()`. Tests call `LOG.unlock()`; `LoggerLockTest` plays the library with `org.example.vendor.Sdk` and a reflective container with `org.example.vendor.Container`.

### Tags: `LOG.tag(...)`, `nanolog.tags`

`LOG.tag(name)` returns a `LOG.Tagged` view with the four shapes of `LOG.Limited` at each level, and `once()` / `atMostEvery(...)`, which return a `Limited` that carries the tag. Both pass the tag to the 4-argument `LOG.isEnabled(current, level, class, tag)` and to `LogEntry.create(..., callerBoundary, tag)`; every level check of `LOG` goes through `accepts`, which calls `ILogger.isEnabled(level, sourceClass, tag)` with `null` for an entry without a tag, and whose default asks the 2-argument method. `ConsoleLogger` keeps the rules of `nanolog.tags` in a second `Rules` snapshot, `tagRules` (read like `nanolog.levels` through `readRuleList`, again by `resetLevels`): a rule for the tag decides before the class, and its threshold counts in `mayBeEnabled`. `CompositeLogger` asks its delegates with the tag. `ConsoleLogger.writeTags` writes `[tag]` after the source, `JsonLogger` `"tags":[...]` after `thread`, `Slf4jLogger` an SLF4J `Marker` (`MarkerFactory.getMarker`), through the marker variants of the level methods only for a tagged entry, so untagged calls reach the backend as before. An entry has one tag (`LogEntry.getTag()`, internal); `getTags()` is a list for the outputs.

### Lazy arguments: `LOG.lazy(...)`

`LOG.lazy(supplier)` returns a `LOG.Lazy`, an argument like any other: the `LogEntry` constructor formats the message, and so calls its `toString()`, only after the level check. `toString()` is `synchronized`, asks the supplier once, keeps `LogEntry.argToString` of the value (or `[FAILED supplier: ...]`, the text of a failing lazy message) and drops the supplier. Never add level overloads that take a `Supplier` for the arguments: they would make existing calls ambiguous, from Kotlin especially (tinylog#94, #50).

### Secrets: `LOG.secret(...)`, `Redaction`

`LOG.secret` returns the one `LOG.SECRET`, whose `toString()` is `***`: it keeps no value, so nothing can format one. The `LogEntry` constructor passes its arguments and its context, after `Contents.bind`, through `Redaction.apply`, which replaces the value of a `LOG.kv` field or a context pair whose key `Redaction.matches` by `LOG.SECRET`, copying the array or map only then; a field without a key stays a plain argument. `matches` compares the key without separators and each word of it (split at non-alphanumerics and at a lower-to-upper case change) with the words of `nanolog.redact`, normalized the same way and read by `LOG.init`; the default is `Redaction.DEFAULT`, the names `Dump` hides. Shown payloads of `LOG.content` go through `Contents.masked` before they are cut: four patterns, for `sk-` keys, AWS access keys, bearer tokens and JSON web tokens. The text of messages is never scanned.

### Payloads: `LOG.content(...)`, `Contents`

`LOG.content` returns an unbound `LOG.Content` holding the value. The `LogEntry` constructor passes its message and arguments through `Contents.bind`, which replaces a payload, or a `LOG.kv` field whose value is one, by a bound copy: the text taken now with `LogEntry.argToString` and the limit of the source class (`Contents.limit`: the rule of the class, its enclosing classes and packages, then `defaultLimit`). The array of the caller is cloned before the first replacement and left as it is. A bound payload is immutable, so `LogEntry.snapshot` keeps it. The context of an entry is bound the same way by `Contents.bind(Map, Class)`, copied only when it holds a payload, so a rule for a package applies to it; only a payload whose `toString()` is called outside an entry uses the global limit. `Contents.render` writes `HIDE` (`-1`) as `[content N chars #hash]` with `Contents.hash`, eight hex digits of a SHA-256 keyed with a random key per JVM (`Contents.Key`, made on first use), so a short payload cannot be found from the log by trying candidates (`error.key` keeps the unkeyed `Units.key`, which must stay the same between runs); a positive limit as the escaped start plus `... [+N chars]`, `SHOW` (`Integer.MAX_VALUE`) as all of the escaped text; `JsonLogger.appendValue` writes a hidden payload as `{"content_len":N,"content_hash":"hash"}`. `Contents.configure` reads `nanolog.content` and the system properties `nanolog.content.<name>` (which include `nanolog.properties`), and `Settings` treats that prefix like the level rules.

### Breadcrumbs: `nanolog.buffer`, `Breadcrumbs`

`Breadcrumbs.threshold` (the ordinal of the highest held-back level, `-1` for off) and `size` are read by `LOG.init`. `LOG.isEnabled` and `LOG.mayBeEnabled` answer `true` for a held-back level, so such calls build their entry; `LOG.dbg` uses `takes` / `mayTake`, the checks without the buffer, and is never held back. `LOG.write` keeps a held-back entry (`Breadcrumbs.keep`) after the captures and before the logger, so a capture gets it at once and the summary and units count it once; an `ERROR` outside units first delivers `Breadcrumbs.drainThread()`. Kept entries are `LogEntry.snapshot()` copies: values rendered unless immutable (null, strings, booleans, characters, `JsonLogger.isNumber`), text cut at `MAX_CHARS`, time, thread and call site kept, `isBreadcrumb()` set; `ConsoleLogger.writeDate` prints their timestamp instead of `getCurrentDate()`. A `Ring` lives per thread (`ThreadLocal`, created by the first kept entry) or per unit (`Units.Scope.ring()`); `drain` returns a header entry, at the highest level present, and the entries. A unit drains its ring in `end` and `LOG.writeUnit` delivers it after its line only when the unit did not succeed.

### Fields: `LOG.kv(...)`, `LOG.Field`

`LOG.kv` returns a `LOG.Field` whose `toString()` is `LogEntry.argToString(value)`, so a `{}` prints it like the bare value and `formatMessage` needs no special case. The `LogEntry` constructor splits the arguments after taking the trailing throwable: when any argument is a field with a key (`isField`), it counts the placeholders, puts every field into `fields` and the fields at an index at or past the placeholder count into `trailingFields`, and leaves the trailing ones out of `args`. Strict mode (`checkCall`) and the `args` and `template` of `JsonLogger` therefore ignore them without code of their own. Without fields the constructor keeps the argument array as it is. `ConsoleLogger.writeFields` and `Slf4jLogger` write the trailing fields with `ConsoleLogger.pair`, the quoting of the context; `JsonLogger` writes all fields with `appendObject` and `appendValue`, the same code as the context, so the two objects have one shape. A field without a key is a plain argument.

### Context: `LOG.context(...)`, `LOG.wrap(...)`, `Contexts`

`Contexts.CURRENT` is a plain `ThreadLocal` (not inheritable: a pool thread would inherit the context of whatever created it) holding a `Contexts.State`: an unmodifiable `LinkedHashMap` of pairs and the open unit, or nothing when both are empty, so threads without a context keep no value. A change never modifies the map: `Contexts.put` installs a copy with the pair, and the `Scope` it returns puts back what its own key held (`present` / `previous`), so scopes of different keys may close in any order; closing twice does nothing. Because maps are never modified, the `LogEntry` constructor keeps `Contexts.current()` as its snapshot without copying. `wrap` takes the map when it is called, replaces the context of the running thread with it and restores that thread's own context in `finally`. The overloads `wrap(Runnable)` and `wrap(Callable)` resolve like `ExecutorService.submit`: a lambda that returns a value picks the `Callable`. Loggers read the pairs from `LogEntry.getContext()`: `ConsoleLogger.writeContext` (after the skipped count, before the stack trace; values quoted by `ConsoleLogger.quoted` when they would not read as one value), `JsonLogger.appendObject` with `appendValue`, which keeps exact JDK number classes, finite floating-point numbers and booleans as JSON literals (shared with the fields of `LOG.kv`, so the JSON shape stays one), and `Slf4jLogger.log`, which puts the pairs into its `MDCAdapter` around `forward` and restores the previous values in `finally`. `MemoryLogger` formats its assertion messages with `showContext` on, whatever the settings.

Context providers (#54): `LOG.addContextProvider` / `removeContextProvider` (kept across `LOG.init()`) and `nanolog.context.provider` (`Contexts.configureProviders`, called by `LOG.init()`; classes are found through `CallerDetection.ThrowableWalk.resolveClass`, and one that cannot be created goes through `printInvalid`) feed an immutable list behind the `volatile` field `Contexts.providers`, configured ones first. The `LogEntry` constructor calls `Contexts.withProviders(pairs)`, so providers run only for entries that are created, that is after the level check. Without providers, or without a key to add, it returns the map of the thread itself, so the cost is one volatile read. Each provider's keys are copied in `ask` before any is used: a provider that throws, or gives a key that is not a `String`, adds none and is reported once per class through the `FAILED` set (every time under `nanolog.diagnostics=all`). The `ASKING` thread local keeps an entry that a provider logs from asking the providers again. Tests call `Contexts.forgetProviders()`; `ContextProviderTest` replaces `DefaultLoggerCreator.environment`, since a real agent environment would print the line of agent mode on `LOG.init()`.

### Print debugging: `LOG.dbg(...)`, `Dbg`, `DbgSource`

`LOG.dbg(T)`, `LOG.dbg(Object, Object, Object...)` and `LOG.dbg()`, and the same three on `LOG.Limited`, check `mayBeEnabled(DEBUG)` before they allocate or walk the stack, then `isEnabled(DEBUG, sourceClass)` (through `Limited.admit` for the limited ones), and only then build the entry in `Dbg.entry`. The two-or-more overload is deliberately not `dbg(Object...)`: with that signature a single `String[]` argument would be spread into its elements and the call would return `void`. A `null` rest array is one `null` value, because javac passes a trailing `null` as the array. `Dbg.message` pairs the values with the expressions only when the text splits into exactly one expression per value; a single value takes the whole text unsplit, since `new HashMap<K, V>()` has a comma outside parentheses. The entry is a `DEBUG` entry built by `LogEntry.createDbg`: the message is complete and the arguments empty, so neither the formatter nor strict mode sees the `{}` a value may contain, and `LogEntry.isDbg()` marks it for `ConsoleLogger` (`DBG`, call site shown even without `showLocation`) and `JsonLogger` (`"dbg":true`).

`DbgSource` reads the text: the file is the package of the frame's class plus `getFileName()` (or the top-level class name when javac ran with `-g:lines`), looked up in `nanolog.sources` or in the roots derived from the class location (`DbgSource.LAYOUTS`, then `src/main/java` and the others under `user.dir`). A source newer than its `.class` is not trusted. `argumentsOnLine` requires exactly one `dbg(` call on the reported line, outside literals and comments, and scans at most `MAX_LINES` following lines for the closing parenthesis; the tokenizer (`tokenEnd`, `literalEnd`) knows strings, chars, text blocks and both comment forms, and the same tokens drive `splitArguments`. Every failure, I/O and invalid paths included, gives `null`, and the result, `null` too, is cached per call site in `DbgSource.CACHE`; `DbgSource.clearCache()` is for tests. `DbgTest` reads its own source, so changing the layout of a call in it changes the expected text.

`Dump` renders values for `Dbg.render` (`Dump.dump`) and, with `nanolog.dump=auto` (`Dump.auto`, read by `LOG.init()` through `DefaultLoggerCreator.readDumpAuto`), for `LogEntry.argToString` (`Dump.argument`). `Dump.kindOf` classifies a class once: arrays, then proxies and lambdas (`Proxy.isProxyClass`, `$$`, `$HibernateProxy$`), then collections, maps and `Optional` whose `toString()` comes from the JDK, then other JDK classes (`TEXT`, never reflected into), records (superclass named `java.lang.Record`, so detection works on Java 8 bytecode), classes with their own `toString()` (`TEXT`) and finally `FIELDS`. Kinds and field lists are cached in `ClassValue`s, which do not pin class loaders. `Dump.clearCache()` replaces them; a test that reaches `kindOf` or `fieldsOf` must call it in `@BeforeEach`, because pitest hot-swaps mutants into a running JVM and would otherwise see results computed by the unmutated code. The two styles share one walk: the dbg style quotes strings and applies `MAX_DEPTH`, `MAX_ITEMS`, `MAX_STRING` and redaction (`isSecret`); the argument style (`plain`) keeps the `toString()` of everything that has one, walks only JDK containers, without limits or redaction, and switches to the dbg style for the `undescribed` kinds (`FIELDS`, `NAMED`). Cycles are tracked by identity on the current path only, so a shared value is printed twice and is not a cycle. Every failure becomes `[FAILED dump()]`. Records cannot be compiled for Java 8, so `DumpTest` compiles one at run time and skips it below Java 16; on Java 8 the record branch is covered only through the mutants it shares with `FIELDS`.

`dbg` is temporary by design, and `Dbg` keeps track of the calls. Both `writeDbg` methods write through `LOG.writeDbgEntry`, which calls `Dbg.ran` with the frame: the call site (`Dbg.site`, `File.java:line`) goes into `Dbg.CALLS`, a synchronized `LinkedHashSet`, and the first call registers the shutdown hook `nanolog-dbg` through `Dbg.shutdownHooks` (a failure to register is swallowed), which prints the list with `Dbg.printCalls`. When the run summary (#62) lands, it takes the list over from the hook. `nanolog.dbg` (`Dbg.mode`, read by `LOG.init()` through `DefaultLoggerCreator.readDbgMode`): `OFF` is checked in `LOG.mayPrintDbg` before `mayBeEnabled`, so an off call walks no stack; with `FAIL`, `writeDbgEntry` reports the call through `LOG.diagnose`, which strict mode shares: `System.err` the first time a call site runs, `onDiagnostic` every time. A test that calls `dbg` must replace `Dbg.shutdownHooks` and call `Dbg.clearCalls()`, as `DbgTest` and `DbgLifecycleTest` do, or the test JVM prints the list when it exits.

`NanologChecks.assertNoDbgCalls` is a text scan, not a parser. It reuses `DbgSource.tokenEnd` and `isBlank`, so comments, strings, chars and text blocks are skipped exactly as when `dbg` reads its arguments, and it matches the token sequences `LOG . dbg`, `LOG :: dbg` and `LOG . name ( ... ) . dbg`. The example `examples/NoDbgCallsLeftTest` runs it on Nanolog's own `src/main/java`, so the library never ships a `dbg` call; Javadoc that shows `LOG.dbg` is fine.

### Caller auto-detection: `CallerDetection`

When the caller does not pass an explicit `Class`, `LOG.findCaller()` asks the locator in the package-private field `LOG.callerLocator` for the first stack frame outside Nanolog. Frames are skipped when their top-level enclosing class is `LOG`, `LogEntry`, `CallerDetection` (the locators themselves; a walk starts inside them) or an `ILogger` implementation (`CallerDetection.isNanolog`). The first remaining frame reaches loggers as `LogEntry.getCaller()` (the call site); the source class is that frame's top-level class (`CallerDetection.topLevel`). `getCaller()` is `null` for calls with an explicit class, which skip the walk. When no frame qualifies (a JVM run with `-XX:-StackTraceInThrowable`, or code running entirely inside an `ILogger` class), the locator returns `Caller.NONE` and the entry is logged without a source class and call site. **This filter is load-bearing**: any new intermediary class between user code and the actual logger must also be skipped there, otherwise it is misreported as the source class. The same holds if you ever add another public façade alongside `LOG`.

The helpers of an application are skipped as well (#25): `nanolog.caller.skip` (`CallerDetection.configureSkip`, called by `LOG.init()`; an invalid name goes through `printInvalid` and is left out, an empty item is ignored) and `LOG.skipCaller(Class...)` (`skipClasses`, kept across `LOG.init()`; tests call `CallerDetection.forgetSkipped()`). Both feed an immutable `Skip` snapshot behind a `volatile` field, replaced on every change; it matches the frame's own class (not its top-level class) by walking its name outwards through `$` and `.` like `ConsoleLogger.findThreshold`, and caches the answer per class. Every locator walks through a `CallerDetection.Walk`, which reads the snapshot once, asks `isNanolog` first and the snapshot second, and remembers the name of the skipped class right before the caller (reset by a frame of Nanolog). That name is the caller boundary: `Caller.boundaryOr(default)` gives it to the entries of `logFromCaller`, `LOG.Limited` and `dbg`, so `Slf4jLogger` hands the helper to a location-aware backend; the lines of timers, units and `Uncaught` keep their own boundary. `CallerSkipTest` uses the helpers `com.nanolaba.logging.wrap.Audit` and `com.nanolaba.logging.wrapper.Tool` (a package with a longer name that `wrap` must not cover); `Slf4jLoggerTest.testASkippedHelperIsTheBoundary` checks the boundary end to end.

There are three locators, and `CallerDetection.best()` picks one when `LOG` initialises:

- `CallerDetection.StackWalk` (Java 9+): a `java.lang.StackWalker` with `RETAIN_CLASS_REFERENCE` that stops at the first qualifying frame and turns only that frame into a `StackTraceElement`. Nanolog is compiled for Java 8, so it reaches `StackWalker` through method handles found by name in its static initializer (a full `MethodHandles.lookup()`: `getInstance` is caller-sensitive and `publicLookup()` refuses it). On Java 8 that initializer fails, and `best()` falls back. Classes are never loaded by name, so a caller in a class loader nobody else can see is found exactly.
- `CallerDetection.LegacyWalk` (Java 8): `sun.reflect.Reflection.getCallerClass(int)` for the class of each frame and `sun.misc.JavaLangAccess.getStackTraceElement(Throwable, int)` for only the frames it looks at, both through method handles found in its static initializer, which fails on any newer JDK (`SharedSecrets` is gone). `getCallerClass(i + 1)` must be called in `find()` itself to match frame `i` of the `Throwable` made there; `getCallerClass` skips the frames of `Method.invoke`, so a class whose name differs from the frame gives way to `LegacyWalk.fallback` (the `Throwable` walk; tests replace it). A `null` class ends the stack: `Caller.NONE`. `LoggerThread` (a top-level `ILogger` thread) gives every locator a stack of Nanolog frames only.
- `CallerDetection.ThrowableWalk`: the stack trace of a new `Throwable`, read through the package-private `ThrowableWalk.stackTraceOf` function (tests replace it to simulate an empty stack and must restore it). Frame classes are resolved by `resolveClass(...)`: the thread's context class loader first, then the loader of `LOG`, without initialization. A frame neither loader can see is skipped instead of aborting the call. "Cannot see" means any `Throwable` from `Class.forName`, not only `ClassNotFoundException`: a `LinkageError` from a child-first loader, GraalVM's `MissingReflectionRegistrationError` (an `Error`), a `SecurityException`. `VirtualMachineError` is caught as well, the same choice as `LogEntry.safeToString` and the guard around a lazy message's `Supplier`.

`best()` goes through `firstWorking(preferred, fallback)`, which takes the preferred locator only if it can be created and finds a caller once. `LOG.findCaller()` also catches anything a locator throws while logging and falls back to `ThrowableWalk`: a logging call never throws. Tests set `LOG.callerLocator` to exercise one locator in particular and restore it in `@AfterEach`. The class-loader tests in `LOGTest` (which compile a caller at runtime into an isolated `URLClassLoader`) pin `ThrowableWalk`, because resolving classes by name is its logic; `testStackWalkFindsACallerThatNoLoaderCanResolve` covers the walker. To count walks, wrap the locator in `CountingLocator`, which implements `ILogger` only so that its frames are skipped too. pitest cannot run `StackWalk` on Java 8 nor `LegacyWalk` on a newer JDK: the profiles `pitest-java8` and `pitest-java9` in `pom.xml`, activated by the JDK, exclude each where it cannot run, so each is mutated on the JDKs that use it.

### Extension point: `ILogger`

Implementations: `ConsoleLogger` (default), `JsonLogger` (extends `ConsoleLogger`, overrides only `createLogString`; hand-written JSON escaping, one entry per line), `Slf4jLogger` (bridge to SLF4J), `MemoryLogger` (keeps entries for tests; `install()` / `close()` swap the logger of `LOG` and restore the previous one) and `CompositeLogger` (fan-out: enabled if any delegate is, each delegate receives only the levels it has enabled; a delegate that throws is reported through `LOG.reportLoggerFailure` and skipped, a throwing `isEnabled` counts as enabled). Custom loggers can be a lambda (`LOG.init(entry -> ...)`) because `ILogger` is effectively single-abstract-method. `isEnabled(level, sourceClass)` defaults to `true`; override it for level filtering. Run-time level changes go through the optional `ILevelControl` interface (`setLevel`, `clearLevel`, `resetLevels`, `withLevel`). Its abstract methods take the level as a string, parsed like `nanolog.level`, so `OFF` is expressible; the `LogEntryLevel` overloads are default methods that pass `Objects.toString(level, null)`, and `ConsoleLogger` / `CompositeLogger` override them only to return their own type for chaining. `ConsoleLogger` implements it, `CompositeLogger` forwards to its delegates that implement it (`withLevel` closes them in reverse order, so a delegate listed twice is restored correctly), and the static `LOG.setLevel(...)` family delegates to the installed logger. A logger without it is reported once per class through the `WITHOUT_LEVEL_CONTROL` set, which `LOG.clearReportedLoggerFailures()` also clears. Arguments are checked by the package-private `ConsoleLogger.isValidLevel` / `isValidName` / `isValidRule`, which `CompositeLogger` calls before forwarding, so a bad argument prints one diagnostic and not one per delegate. `mayBeEnabled(level)` also defaults to `true` and must never be `false` for a level that `isEnabled` accepts for some class, `null` included. `ConsoleLogger` and `CompositeLogger` implement it, and both answer `true` for a subclass that overrides `isEnabled` without `mayBeEnabled`. They detect such a subclass once in the constructor through `LoggerIntrospection.overridesIsEnabled`, which uses reflection and also answers `true` when the lookup fails, for example in a native image. It lives outside `LOG`, so creating a logger does not initialise `LOG`; initialising it inside a test would print its configuration diagnostics into that test's captured output. `LOG.log(...)` short-circuits on `isEnabled` before constructing the `LogEntry`, and `Supplier<Object>` messages are only resolved past that check, so lazy-message semantics depend on this order (`NoUnnecessaryCallsTest`, `MemoizingMessageTest`).

- `ConsoleLogger` reads its configuration in the no-arg constructor: `nanolog.level`, `nanolog.levels`, `nanolog.level.<package or class>` and `nanolog.console.*`. Setters called afterwards override what it read, but package and class rules are checked first in `isEnabled` and beat the five boolean switches. The rules live in an immutable `Rules` snapshot behind the `volatile` field `rules`: the thresholds by name, their lowest value, and a per-snapshot cache of thresholds resolved per `Class` (`findThreshold` walks from the class name outwards through `$` and `.`). Every rule change goes through the `synchronized` `replaceRule`, which copies the map, changes one name and swaps in a new snapshot; because the cache belongs to the snapshot, a thread that resolved a class against old rules cannot leave a stale entry in the new cache. The five switches are `volatile`; `setLevel(level)` and `resetLevels()` are `synchronized` so concurrent calls do not mix their switches. `RuntimeLevelsTest.testLevelStateIsSafelyPublished` asserts these modifiers, since pitest mutates neither. `mayBeEnabled` combines the lowest threshold of the current snapshot with the switches. One rule at `TRACE` therefore makes every `trace` call without a class walk the stack again. An invalid value goes through `DefaultLoggerCreator.printDiagnostic` and is ignored; configuration must never throw. `printDiagnostic` escapes control characters and U+2028/U+2029 as `\u000a`-style escapes, so a diagnostic is one line whatever it echoes (a level from a request, an exception message, a template); send new diagnostics through it, never straight to `System.err`.
- `ConsoleLogger` writes `ERROR` to `System.err`, everything else to `System.out`. Its single `SimpleDateFormat` is shared by all threads, so `writeDate` reads it once and formats inside `synchronized (format)`; keep that when touching the date code. The zone lives on the format: `setTimeZone` sets it inside the same monitor (`setZoneOf`), and `setDateFormat` gives a later format the zone of the logger when one was set. `nanolog.console.timeZone` is checked because `TimeZone.getTimeZone` takes an unknown ID for GMT; `dateFormat=iso` is `ISO_DATE_FORMAT`. `ConsoleTimeZoneTest` sets the zone of the JVM to `Pacific/Honolulu` and puts it back, so it tells the zones apart on a machine in UTC.
- `sourceLength` (#29) abbreviates the full source name in `getSourceName` with `ConsoleLogger.abbreviate`, the algorithm of `%logger{n}` in Logback. It cuts only the segments of the package, taken from the binary name, and keeps the rest of the full name, so a nested class keeps `Outer.Inner`. The names are cached per class in an `Abbreviations` snapshot behind a `volatile` field that `setSourceLength` replaces, so a length and its names always go together. `ConsoleSourceLengthTest` checks the examples of the Logback manual.
- `Slf4jLogger` caches one `org.slf4j.Logger` per source class in a `ConcurrentHashMap`. A `null` source class maps to the SLF4J `ROOT` logger (`ConcurrentHashMap` rejects `null` keys). An entry without a message is passed as an empty string, not `"null"`. The formatted message is passed as a plain string, so SLF4J never sees the `{}` arguments; markers are unsupported. When the SLF4J logger is a `LocationAwareLogger` (Logback, Log4j 2), `Slf4jLogger` calls its `log(marker, fqcn, ...)` with `LOG`'s class name as the caller boundary and `null` arguments, so the backend reports the code that called `LOG` and does not format the message again; keep every frame between user code and the logger inside `LOG` or skipped by the backend, or the boundary breaks. Tests use a package-private constructor that takes the logger factory, with `java.lang.reflect.Proxy` loggers, because only one SLF4J provider (slf4j-simple, not location-aware) can be bound in the test JVM; another one also takes the `MDCAdapter`, since slf4j-simple keeps no MDC (`ContextTest` passes a `BasicMDCAdapter`).

### Bootstrap: `DefaultLoggerCreator`

On `LOG` class init (and on any `LOG.init()` with no args), a default `ILogger` is resolved as follows:

Settings are looked up by `DefaultLoggerCreator.getProperty(name)`: the system property first, then the environment variable of the same name in upper case with dots replaced by underscores (`nanolog.logger` → `NANOLOG_LOGGER`). Tests replace the package-private `DefaultLoggerCreator.environment` function instead of the real environment and must restore it in `@AfterEach`.

1. Load `nanolog.properties` from the classpath (or the resource named by `nanolog.config` / `NANOLOG_CONFIG`) through the thread's context class loader, falling back to the class's own loader when the context loader is `null`. The first copy is read; `reportSeveralFiles` lists them all through `getResources` and prints one diagnostic when there are several and one is a `jar:` URL (two directories, main and test resources, are an override), after `readDiagnostics`, so the file can silence it. `SeveralConfigFilesTest` builds directories and jars in a temporary folder behind a `URLClassLoader` without a parent. Copy **only keys with the `nanolog.` prefix** (`DefaultLoggerCreator.PROPERTY_PREFIX`) into `System` properties, and only where neither a system property nor the environment variable is set, so the precedence is `-D`, environment, file, and the file cannot alter unrelated JVM settings.
2. If `nanolog.logger` (or `NANOLOG_LOGGER`) is set, `Class.forName(...).getConstructor().newInstance()` that class.
3. Otherwise, return `new ConsoleLogger()`.

Failures in step 2, and a missing file named by `nanolog.config`, are printed to `System.err` with a `[NANOLOG]` prefix and fall through to `ConsoleLogger`. An `IOException` while reading the file is rethrown as `RuntimeException` and would break `LOG`'s static initializer.

After loading the file, `loadPropertiesFromFile` hands the `nanolog.*` system properties, the environment variables and the keys of the file to `Settings.findings`, and prints one `[NANOLOG]` line per unknown setting (`reportUnknownSettings` swallows any failure). `Settings.KNOWN` is the one list of keys Nanolog reads, with the package rules `nanolog.level.<name>` on top; `SettingsTest` fails when a `PROPERTY_*` constant of `DefaultLoggerCreator` or `ConsoleLogger` is missing from it or from a settings table of the README, so a new setting needs all three. A system property whose value equals the file's is a key the file copied, and is reported with the file only. Unknown keys are reported under Nanolog's own namespaces (`Settings.NAMESPACES`: `buffer`, `caller`, `console`, `content`, `context`, `exception`, `junit`, `level`, `run`, `unit`, and keys without a dot); elsewhere, which is where a custom logger keeps its keys, only when `Settings.closest` finds a known key within one edit (names shorter than six characters) or two. `nanolog.version` and `NANOLOG_VERSION` (`Settings.VERSION`) are never reported: they are the Maven property of the dependency version, which Surefire passes to the forks as a system property (#94). Environment variable names come from `DefaultLoggerCreator.environmentNames`, values from `environment`; a test that controls the environment replaces both.

`createDefaultLogger` passes the configured logger through `RunLog.attach`, which returns it unchanged unless `nanolog.run=on`; then it returns a `RunLog.Tee` (a `CompositeLogger`) of it and the `RunLog` of the JVM. `LOG.install`, behind `LOG.init(ILogger)` and `MemoryLogger.install()`, passes every logger through `RunLog.with`, which adds the open run log unless the logger writes it already, so the file keeps every entry after the application installs its own logger (#90); `LOG.getLogger()` returns the tee, and `Tee.log` passes an entry that an outer tee of the same thread is passing on (`PASSING`) to its logger only, so a decorator of that tee, or `MemoryLogger.installForwarding()`, writes the run log once (#95); a tee answers `isEnabled` and `mayBeEnabled` for its logger alone, through the guards of `CompositeLogger`, so `LOG.isXxxEnabled` and lazy arguments do not change when the run log is added (#103), and only the tee that `attach` makes in agent mode around the console `Agent.shorten` shortened (`Agent.isConsole`) is `widened` and adds the levels of the run log, which are those of that console without agent mode; and the "Logger replaced" diagnostic compares and names the loggers through `RunLog.unwrap`. `RunLog` is a `ConsoleLogger` subclass, so it reads the levels and is an `ILevelControl` like the console, and the composite routes each entry by the levels of each delegate; it is opened once per JVM (`RunLog.current`, `opened`; `RunLog.reset()` for tests), so repeated `LOG.init()` calls keep one file. Its constructor reads the console settings a second time, so `RunLog.open` builds it inside `DefaultLoggerCreator.quietly`, which mutes `printDiagnostic` on the current thread. `open` writes `runs/<id>.log` and `runs/<id>.errors.log` through unbuffered `Files.newOutputStream` streams, makes `latest.log` and `latest.errors.log` hard links to them through `RunLog.linker` (tests make it fail), and prunes `runs/` by file name, which starts with the time, deleting the errors file and the list of each run it deletes (a `.summary.log` is not a run). It also deletes `latest.summary.log`, the list of the run before. `writeSummary`, which the run summary calls at the end, writes `runs/<id>.summary.log` and links `latest.summary.log` to it only while `latest.log` is still the file of this run, so both names belong to one run (#99); it returns the path to print, as `shownFile()` does, or `null` with one diagnostic after an `IOException`. `shownFile()` and `shownErrorsFile()`, behind every printed path, name `latest.log` while `Files.isSameFile` finds it is still the file of this run, otherwise the run's own file: another Surefire fork that starts later in the same directory takes `latest.log` (#93). In a test JVM of a build tool (`RunLog.testWorker` reads `sun.java.command`: Surefire's `ForkedBooter` or its `surefirebooter*.jar`, Gradle's `GradleWorkerMain`), `attach` sets `own` and both name the run's own file from the start, since any other fork may take `latest.log` later (#96); `AbstractLoggerTest` sets `sun.java.command` to a plain main class for every test, because the tests themselves run in a Surefire fork. `log` is synchronized: one line per entry to the run file and, for `WARN` and above, a one-line form (`brief` turns the stack trace into the exception's `toString()`) to the errors file; each stops at `maxSize` with a note, and an `IOException` closes both with one diagnostic. In agent mode it is on by default and leaves the path to the agent line; the run summary (#62) is meant to repeat it.

`ConsoleLogger.createLogString` passes the whole entry through `applyMultiline` (`nanolog.console.multiline`): `keep` returns it unchanged; `indent` and `escape` drop trailing line breaks, escape C0 controls except the tab, DEL, C1 and U+2028/U+2029 as `\uXXXX`, and either start every further line with a tab (unless it starts with one, as stack frames do) or write `\r` and `\n` as two characters. `JsonLogger` overrides `createLogString` and is not affected; `RunLog` follows the setting it reads, while agent mode sets `escape` only on the console.

`ConsoleLogger.log` colours the level word when `nanolog.console.color` resolves to colours. `Colors.enabled` decides when the mode is set: by the constructor, `setColor`, or `useAgentDefaults`, which defaults it to `never`. `log` writes the level once more with `writeLevel` and colours it only if the text of `createLogString` starts with it, so `JsonLogger` and custom formats stay plain. `createLogString` itself never contains colour codes, so the run log (`RunLog.log`), the assertion messages of `MemoryLogger` and anything else that formats an entry get none. `auto` reads `NO_COLOR`, `FORCE_COLOR` and `TERM` through `DefaultLoggerCreator.environment`, and the terminal through the package-private seams `Colors.console`, `Colors.isTerminal` (`Console.isTerminal()` of JDK 22+, looked up by reflection) and `Colors.properties` (`os.name`: Windows stays off, since its console shows the codes as text unless the program enables virtual terminal processing). Tests replace the seams and restore them. The test JVM gets `NANOLOG_CONSOLE_COLOR=never` from the POM, so a `FORCE_COLOR` of the developer's shell cannot colour the output the tests compare.

Agent mode (`nanolog.agent`, class `Agent`): `createDefaultLogger` calls `Agent.detect()` after loading the file, which returns what turned it on (`AI_AGENT=claude-code`, `nanolog.agent=on`) or `null`; detection reads the variables through `DefaultLoggerCreator.environment`, so tests control it. For a `ConsoleLogger` (or subclass) `Agent.shorten` calls the package-private `ConsoleLogger.useAgentDefaults()`, which sets `defaultThreshold` to `WARN` (also used by `resetLevels()`) and re-reads `nanolog.level`, `showDate`, `nanolog.console.multiline`, `nanolog.console.color`, `nanolog.console.repeats` and `nanolog.exception.*` with the agent defaults inside `quietly`: a setting that is given wins, an invalid one gives the agent default, and the constructor has already reported it. Any other logger is left alone. `RunLog.attach(logger, agent)` defaults `nanolog.run` to `on` and does not print its own path line; `Agent.announce` prints the one agent line, once per JVM (`Agent.reset()` for tests). `LOG.init()` sets `Dbg.ignoreLevels` from a second, quiet detection: then `LOG.mayPrintDbg`, `LOG.printsDbg` (also for the `dbg` methods of `LOG.Limited`) and `CompositeLogger.log` let every `dbg` entry through whatever the levels. `Slf4jLogger` and `JulLogger` would still lose one in their backend, so they give a `dbg` entry whose level the backend has off for the class to `Dbg.print`, a `ConsoleLogger` with the agent defaults and `repeats=keep`, created once on first use (#105).

Captures of one thread (`MemoryLogger.capture()`, `captureForwarding()`): `LOG.startCapture` adds the `MemoryLogger` to the copy-on-write list of the current thread in `LOG.CAPTURED` and increments `LOG.CAPTURES`; `endCapture`, called by `close()` from any thread through the list the capture keeps, removes it once. `LOG.captures()` reads `CAPTURES` first and the `ThreadLocal` only when it is not zero, so logging without a capture pays one volatile read. While the thread has a capture, the guarded `LOG.isEnabled` and `LOG.mayBeEnabled` answer `true` for every level; `write` then gives the entry to every capture of the thread and to the logger only if all of them forward and the logger itself accepts it (`LOG.accepts`, the former body of `isEnabled`), and `diagnose` follows the same rule for findings. Entries of other threads, pools included, are not captured; `LOG.wrap` (#26) is the place to carry a capture over. A capture keeps entries only from `keptFrom`, the logger installed when it opened (`null` for `captureForwarding()`), so a logger the test installs inside it still receives them; `everyLevel` is set for `capture()` and `captureForwarding()`, and `LOG.isEnabled` / `mayBeEnabled` answer `true` only for such a capture. `MemoryLogger.buffer()` is the capture of `NanologExtension`: it takes only the entries the logger accepts and holds them back from it.

`NanologExtension` (JUnit 5, compiled against the `provided` `junit-jupiter-api`) opens a buffer (`Held`, around `MemoryLogger.buffer()`) in `beforeAll` for the class and in `beforeEach` for each test, and keeps it in `BUFFERS` by unique ID, not in the `ExtensionContext` store, which JUnit 5.13+ closes before the `TestWatcher` callbacks. `LOG.pauseBuffers()` first takes the buffers of the extension that are open on the thread off it, and `Held.close()` (`afterEach`, `afterAll`) puts them back with `LOG.resumeBuffers`, so each entry is held back once: the class buffer holds what the class logs outside its tests, `@BeforeAll`, `@AfterAll` and the creation of each test instance, where `SpringExtension` starts the context (#100); with `PER_CLASS` the instance is created before `beforeAll`. `testFailed` marks the classes around the test (`Held.failed`), and `afterAll` writes the log of the class, framed as `class <Name>`, when that is set or `getExecutionException()` is present, after the tests. `testFailed` writes the entries to `keptFrom` between two `--- log of ... ---` lines on `System.out` (unless `nanolog.junit.output=none`); `testSuccessful` and `testAborted`, and a failure with `none`, give them to `RunLog.replay`, which writes them to the run log only when `keptFrom` is a `CompositeLogger` that contains it. `nanolog.junit.output` is read once per JVM (`NanologExtension.reset()` for tests); with `all` no buffer is opened. `META-INF/services/org.junit.jupiter.api.extension.Extension` registers it when JUnit autodetection is on. `NanologExtensionTest` runs nested fixture classes through a `Launcher` of its own; the fixtures call `onlyThroughRun()`, an assumption, so any other runner, Surefire or pitest, skips them.

Run summary (`nanolog.summary`, class `Summary`): `LOG.init()` reads `Summary.mode` through `DefaultLoggerCreator.readSummaryMode(agent)` (`on` by default in agent mode, `off` otherwise) and, unless it is `OFF`, registers the shutdown hook `nanolog-summary` once per JVM through `Summary.registerHook` (`Summary.shutdownHooks` for tests). `LOG.write` calls `Summary.count`, through `countInSummary` while the mode is not `OFF`, for every entry it delivers or holds back as a breadcrumb and for one that the buffer of `NanologExtension` takes (a capture without `everyLevel`, which passes it on when the test ends), but not for one that `MemoryLogger.capture()` keeps from the logger or that only a capture takes, so the summary describes the run log it names (#97): lock-free counters per level and per kind, at most `MAX_KEPT` kinds: the key is the level and the call site, so a call site that builds its messages from data is one kind (#92), which keeps its first message (cut to `MAX_TEXT`, and shown by `firstLine` as its first line that is not blank, with `...` when more follows, #98) and the hashes of up to `MAX_MESSAGES` + 1 different messages for `(N different messages)`; a call with an explicit class has no call site, so its key is the level, the class and the line shown, and the short trace of the first error with an exception, rendered once. `Summary.printOnce` prints the end of the run the first time it is called: the summary for `ON`, or for `ERRORS` after a `WARN` or `ERROR`, otherwise `Dbg.printCalls()`. Before printing the summary it calls `writeList`, which sorts every kind by level and then by its `place` and, while the run log is open, passes their lines (`Kind.line`, as in the summary) to `RunLog.writeSummary`; `lines(Path)` adds `; the full list is in <path>` to the line that counts the kinds not shown, and `lines()` names no list (#99). Two callers race for it: the hook and the JUnit listeners registered in `src/main/resources/META-INF/services` and compiled against the `provided` `junit-platform-launcher`. `SummaryListener` (a `TestExecutionListener`) calls `Summary.planFinished()`, which prints only while no launcher session is open; `SummarySessionListener` (a `LauncherSessionListener`, JUnit Platform 1.8+, a class of its own so that an older platform can still load `SummaryListener`) counts the open sessions and prints when the last one closes, if a plan finished in this JVM. Surefire 3.x opens one session per fork and, with `forkCount` above 1, runs each test class as a plan of its own (#89); it also opens and closes a session in a JVM that runs no test, which must print nothing. Gradle runs one plan per worker inside one session. The listener is needed because Surefire drops the output of shutdown hooks in its forked JVM (measured with Surefire 3.2.5), which also hid the `dbg` list of #60. `Dbg.ran` registers the same hook, so a `dbg` call is listed at the end whatever the mode. Tests replace `Summary.shutdownHooks` and call `Summary.reset()`, which also forgets the `dbg` calls; `Summary.mode` is reset to `OFF` afterwards. Nanolog's own test JVM loads `SummaryListener` too, from `target/classes`; with the mode `OFF` and the calls reset it prints nothing.

The test JVM runs with `NANOLOG_AGENT=off` (`environmentVariables` of Surefire and pitest in `pom.xml`), so a build started by a coding agent behaves like CI; a test that needs agent mode replaces `DefaultLoggerCreator.environment` and `environmentNames` with a map, where the variable is absent.

Do not add a `nanolog.properties` to `src/test/resources`: it would be picked up by every test's `LOG` initialization. Tests use `nanolog.config` pointing at `test.properties` / `mixed.properties` / `levels.properties` instead, and clear every `nanolog.*` system property they or the file set.

### Stack traces: `ConsoleLogger.stackTraceOf`, `ShortStackTrace`

`ConsoleLogger.stackTraceOf` (also used for the `stackTrace` field of `JsonLogger`) returns the output of `printStackTrace` verbatim unless `exceptionExclude` or `exceptionMaxFrames` is set; only then does it use `ShortStackTrace`, Nanolog's own printer with the layout of `printStackTrace` (`Caused by:`, `Suppressed:` with indentation, `... N more` for frames shared with the enclosing trace, `[CIRCULAR REFERENCE: ...]` in the Java 9+ wording). Keeping the default on `printStackTrace` is what makes it byte-identical on every JDK and for throwables that override `printStackTrace`. `ShortStackTrace` lets every failure through and `stackTraceOf` falls back to `printStackTrace`, then to `[FAILED printStackTrace()]`. Because that fallback would hide a broken printer behind correct-looking output, `ShortStackTraceTest` tests `ShortStackTrace.of` directly; keep it that way when changing the printer.

### Message formatting: `LogEntry.formatMessage()`

Parameterized messages use `{}` placeholders (SLF4J-style). Escaping is non-trivial and has dedicated tests in `LogEntryTest`:

- `\{}` is a literal `{}`; the argument is **not consumed** (the consumer loop decrements `argIndex`).
- `\\{}` is a literal `\` followed by a substitution (both escapes consumed, the argument is substituted).
- Missing arguments leave `{}` in place; extra arguments are ignored.

Primitive arrays are rendered via `Arrays.toString`, object arrays via `Arrays.deepToString`; if `deepToString` throws because of an element's `toString()`, `arrayToString` falls back to rendering element by element so only the broken element becomes `"[FAILED toString()]"`. Every `toString()` call goes through `safeToString`, including those in `LogEntry.toString()`, and stack traces go through `ConsoleLogger.stackTraceOf`, which turns a throwing `printStackTrace` into `[FAILED printStackTrace()]`. Preserve this "logging never throws" guarantee when changing formatting code; the README promises it.

## Tests

- `AbstractLoggerTest` redirects `System.out` / `System.err` into buffers; `ConsoleLoggerTest` and `Slf4jLoggerTest` assert exact output lines (slf4j-simple is configured by `src/test/resources/simplelogger.properties`).
- `LOGTest` drives every overload and asserts the `LogEntry.toString()` representation; it also contains the class-loader scenarios.
- `DefaultLoggerCreatorTest` manipulates system properties and the context class loader and must clean up in `@AfterEach`.
- Classes under `src/test/java/com/nanolaba/logging/examples` are not tests: they are the README's code samples and only need to compile. The exception is `NoDbgCallsLeftTest`, the README's sample of a test, which runs.

## Dependencies

- `slf4j-api` is **`provided`**: required only if the consumer uses `Slf4jLogger`. Do not promote it to `compile` scope; that would force SLF4J onto every downstream user and defeat the "zero dependencies" claim in the README.
- `junit-jupiter-api` is **`provided`** as well: only `NanologExtension` uses it, in tests that have JUnit Jupiter anyway.
- `junit-platform-launcher` is **`provided`** for the same reason: only `SummaryListener` and `SummarySessionListener` use it, and only the JUnit Platform loads that class, in a test run that has the launcher anyway. Keep its version in step with `junit5.version`.
- `junit-jupiter`, `slf4j-simple`, `commons-lang3`, `pitest-junit5-plugin` are all test-scope.
- JMH (`jmh-core`, and `jmh-generator-annprocess` as an annotation processor) exists only in the `benchmark` profile, in test scope; see [Benchmarks](#benchmarks).
- The jar manifest declares `Automatic-Module-Name: com.nanolaba.nanolog` (configured on `maven-jar-plugin`); keep it stable, modular applications depend on it.

## Release build

The default build signs artifacts with GPG (`maven-gpg-plugin` 3.x, through gpg-agent) and publishes via `central-publishing-maven-plugin` with `autoPublish=true`. For local development use `mvn test` / `mvn compile` / `mvn verify -Dgpg.skip=true`; avoid `mvn deploy` unless you are actually cutting a release. Plugins are resolved from Maven Central only; do not reintroduce snapshot plugin repositories.

Release checklist:

1. Set the release version in `pom.xml` and the `nanolog.stableVersion` property to the same value, update the changelog section in `README.src.md`, run `mvn compile`, commit the regenerated README files, `llms.txt` and `SKILL.md` together with the sources.
2. `mvn clean deploy` on JDK 11 or newer, so the jar gets its module descriptor (signs the artifacts and publishes them to Maven Central), then tag the release commit (`git tag -a vX.Y -m "Nanolog X.Y"`; a patch release such as 1.4.1 is `vX.Y.Z`) and push the branch and the tag.
3. **Create a GitHub release for the tag.** Every published version must have one: `gh release create vX.Y --verify-tag --title "<title>" --notes-file notes.md --discussion-category Announcements`, which also opens a discussion of the release. The notes are the `### X.Y` changelog section from `README.src.md` (English), grouped into "New" / "Fixes" / "Documentation and build", followed by the Maven coordinates and a `compare/vPREV...vX.Y` link; the `v1.1` release is the reference layout. Do not publish it as a draft or pre-release.
   - **Title and first line.** A release without headline features is titled `vX.Y`. A release with them names them, the measured one first, as in "Nanolog 1.4: fewer tokens for AI coding agents, LOG.dbg and wide events"; the first line of the notes gives the measured saving and links to the README section *Fewer tokens: logs for AI coding agents*. Token numbers come only from `src/tokens/RESULTS.md`, with the tokenizer named; re-measure with `src/tokens/measure.py` first if the output of agent mode changed since.
   - **Feedback.** The notes end with a "Feedback" block: the discussion of the release, [Q&A](https://github.com/nanolaba/nanolog/discussions/categories/q-a) and the [issue forms](https://github.com/nanolaba/nanolog/issues/new/choose).
   - **Social preview.** When the release changes what the project leads with, edit `assets/social-preview.html`, regenerate `assets/social-preview.png` with the command in its header (headless Chrome, 1280×640) and upload the PNG in *Settings → General → Social preview*; GitHub has no API for it.
4. Once the version is on Maven Central, paste *Try it* of the README into a new Maven project and a new Gradle Kotlin DSL project: it compiles, and `LOG.dbg` prints the expression text.
5. Bump `pom.xml` to the next `-SNAPSHOT`, run `mvn compile`, commit the regenerated README files.

## Conventions

- Commit messages: English, imperative subject line, body explains the why.
- Issues and questions: `.github/ISSUE_TEMPLATE` has the forms for a bug, a feature and the documentation, and `config.yml` sends questions to Discussions Q&A (whose form is `.github/DISCUSSION_TEMPLATE/q-a.yml`) and vulnerabilities to private reporting; blank issues stay enabled. A question filed as an issue is answered there and labelled `question`, never closed as the wrong place. English and Russian are both fine everywhere. A new field of a bug report goes into `bug_report.yml`, not into a comment asking for it.
- Keep the public API additive; this library is consumed from Maven Central.
- Every production change ships with tests that kill the corresponding pitest mutants and, where user-visible, with a README change in `README.src.md`.
- A killer feature (an issue labelled `killer-feature`) is not done until its SEO work is done too. Every such issue has an "SEO" section with the search phrases and a checklist; work through it. It covers a README section titled with the search phrase plus a "Why Nanolog" bullet (EN and RU), the GitHub description and topics (`gh repo edit`), `<description>` in `pom.xml`, the description in `agent-guide.src.md`, the first sentence of the Javadoc and the release notes. Claims stay honest: no keyword stuffing, comparisons with versions and dates. The baseline is issue #69.
