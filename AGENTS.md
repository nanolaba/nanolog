# AGENTS.md

Guidance for coding agents (Claude Code, Codex, Copilot and others) working in this repository. `CLAUDE.md` only points here.

## Build & Test

Maven project targeting **Java 8** (`maven.compiler.release=8`). Do not introduce Java 9+ APIs in `src/main`. Tests may rely on a JDK (not a JRE): `LOGTest` compiles a class at runtime with `javax.tools.ToolProvider`.

- Full build: `mvn verify -Dgpg.skip=true` (the default `verify` tries to GPG-sign artifacts)
- Tests + mutation analysis: `mvn test`
- Single test class: `mvn test -Dtest=LOGTest`
- Single test method: `mvn test -Dtest=LOGTest#methodName`
- Compile only (also regenerates the README files): `mvn compile`
- Fast JUnit-only loop while developing: `mvn test-compile surefire:test -Dtest=LOGTest`

CI (`.github/workflows/ci.yml`) runs `mvn -Dgpg.skip=true -Dcheck=true verify` on JDK 8, 11, 17 and 21. Actions are pinned to commit SHAs and the token is read-only; keep it that way when editing the workflow.

### Javadoc

`maven-javadoc-plugin` runs with `doclint=all` and `failOnWarnings=true`, so every public and protected class, constructor, method, field and enum constant needs a Javadoc comment, with `@param` / `@return` tags and a first sentence before them (JDK 18+ rejects a tag-only comment as "no main description"). JDK 8 javadoc does not report missing comments at all, so check with a newer JDK as well, as CI does: `JAVA_HOME=<jdk17+> mvn javadoc:javadoc`. The plugin skips a run whose sources look unchanged: delete `target/maven-javadoc-plugin-stale-data.txt` (and `target/reports`) to force it. The level overloads of `LOG` share wording per signature shape; keep a new overload consistent with its siblings.

### Pitest mutation coverage (important)

The `test` phase is wired to run **pitest-maven** with `mutationThreshold=100`. Any surviving mutant fails the build, not just failing unit tests. When changing production code:

- `mvn test` covers both JUnit and mutation analysis; run it before every commit.
- If a mutant survives, add a test that would catch the mutation rather than weakening the threshold. "Mutations with no coverage" means a line is never executed by tests: cover it.
- Pitest's default mutators do not remove `synchronized` blocks, so thread-safety fixes need a deterministic test of the contract instead (see `ConsoleLoggerTest.testDateFormatIsGuardedByItsMonitor`).

### Benchmarks

JMH benchmarks live in `src/jmh/java` (`com.nanolaba.logging.benchmark`) and build only with the `benchmark` profile, which adds JMH in `test` scope. The default build, CI, pitest and the published jar never see them.

- Run all: `mvn -P benchmark test-compile exec:exec` (about 4 minutes).
- Another JVM: `-Djmh.java="C:/Program Files/Java/jdk-17.0.2/bin/java"`; the classes are Java 8 bytecode, so one build runs on every JDK.
- JMH options: `-Djmh.args="DisabledCallBenchmark -rf text -rff result.txt"`; `-Djmh.args=-l` lists the benchmarks.
- Benchmarks use only the 1.2 API (`LOG.init`, the `ConsoleLogger` setters, `-Dnanolog.level.<name>` set before construction), so the same classes run against the sources of an older commit compiled on their own: that is how the "before #16" numbers were taken. Keep it that way.
- Results, with the JDK, CPU and OS they were measured on, are in `src/jmh/RESULTS.md`. Re-measure and update it, and the numbers quoted in README *Thread safety and performance*, after a change to caller detection or the level check.

## Architecture

Nanolog is a tiny SLF4J-compatible logging facade: a handful of source files in one package, no runtime dependencies. The whole public API is static methods on one class; there are no per-class logger fields.

### The single entry point: `LOG` (`src/main/java/com/nanolaba/logging/LOG.java`)

All logging goes through static methods on `LOG` (`LOG.info(...)`, `LOG.debug(...)`, ...). Each level has the same set of overloads: explicit source `Class`, `Throwable`, `Supplier<Object>` for lazy messages, `String` + `Object...` for parameterized messages, and since 1.1 the combinations `(Throwable, String, Object...)` and `(Class, Throwable, String, Object...)`. All overloads funnel into the private `LOG.doLog(...)`: overloads with an explicit `Class` through the public `LOG.log(level, class, throwable, supplier, args...)`, the others through `logFromCaller(...)`, which first asks the guarded `ILogger.mayBeEnabled(level)`, walks the stack only when it says `true`, and then passes the detected source class and caller frame. The no-argument `isXxxEnabled()` methods do the same through `isEnabledForCaller`, so a level that is off for every class costs no stack walk; `LevelCheckBeforeStackWalkTest` counts walks through `CountingLocator`. `doLog` checks `isEnabled` and hands a `LogEntry` to the configured `ILogger`. Both calls into the logger are guarded: a logger that throws is reported once per class through `LOG.reportLoggerFailure` (tests call `LOG.clearReportedLoggerFailures()`), a throwing `isEnabled` counts as enabled, and an entry the logger fails to write goes to the `LOG.Fallback` `ConsoleLogger`, which prints every level to `System.err`. The `isXxxEnabled()` methods go through the same guard. In strict mode (`nanolog.strict`, read by `LOG.init()`) it first runs `checkPlaceholders`, which prints one `[NANOLOG]` line per mismatched template and also hands every occurrence to `ILogger.onDiagnostic` (guarded: a throwing logger is reported through `reportLoggerFailure`), so `MemoryLogger.assertNoDiagnostics()` sees a template that an earlier test already printed. It must never throw or change the entry. Tests that enable it call `LOG.clearReportedTemplates()`. The fields `LOG.logger` and `LOG.strict` are `volatile`, so a logger installed while other threads log (`MemoryLogger.install()` in a test) is seen by them; `LOGTest` asserts the modifier because pitest does not mutate it. Keep any new field that every logging call reads `volatile` as well. When adding an overload, add it to all five levels and extend the per-level tests in `LOGTest`, which assert `LogEntry.toString()`.

Overload resolution matters: the `Object` and `Supplier` forms win in the non-varargs phases, the varargs forms only apply when extra arguments are present. Do not add overloads that make existing calls ambiguous (`LOG.info(e, "text")` must keep resolving to `(Throwable, Object)`).

### Rate limiting: `LOG.once()`, `LOG.atMostEvery(...)`

Both return a `LOG.Limited` view with four overloads per level. The view is nested in `LOG`, so caller detection skips its frames like those of `LOG`. `Limited.log` checks in this order: `mayBeEnabled`, caller detection, `isEnabled`, then `LOG.acquire(callSite, periodNanos)`, and only then resolves the message; a disabled call is never counted. `acquire` keys a `RateState` by the call site (`StackTraceElement`) in `LOG.LIMITS`, which needs no eviction because call sites are bounded by the code. `RateState` holds two `AtomicLong`s: a call gets through only by winning the compare-and-set of the last entry time, and every other call increments the skipped count, so each call is logged or counted exactly once (`RateLimitTest.testConcurrentCallsAreLoggedOrCountedExactlyOnce`). `once()` is a period of `Long.MAX_VALUE`; a period of zero or less, or a `null` unit, limits nothing and prints no diagnostic, because a loop would flood `System.err`. A call without a call site (`Caller.NONE`) is not limited. The clock is the package-private `LOG.nanoClock`, and `LOG.clearLimits()` forgets the state; tests replace and restore both. The skipped count reaches loggers as `LogEntry.getSkippedCount()`. Entries built by `Limited` carry `LOG.Limited` as their package-private `LogEntry.getCallerBoundary()`, which `Slf4jLogger` passes to location-aware backends instead of `LOG`: a boundary of `LOG` alone would make Logback and Log4j report the frame of `Limited` as the call site.

### Print debugging: `LOG.dbg(...)`, `Dbg`, `DbgSource`

`LOG.dbg(T)`, `LOG.dbg(Object, Object, Object...)` and `LOG.dbg()`, and the same three on `LOG.Limited`, check `mayBeEnabled(DEBUG)` before they allocate or walk the stack, then `isEnabled(DEBUG, sourceClass)` (through `Limited.admit` for the limited ones), and only then build the entry in `Dbg.entry`. The two-or-more overload is deliberately not `dbg(Object...)`: with that signature a single `String[]` argument would be spread into its elements and the call would return `void`. A `null` rest array is one `null` value, because javac passes a trailing `null` as the array. `Dbg.message` pairs the values with the expressions only when the text splits into exactly one expression per value; a single value takes the whole text unsplit, since `new HashMap<K, V>()` has a comma outside parentheses. The entry is a `DEBUG` entry built by `LogEntry.createDbg`: the message is complete and the arguments empty, so neither the formatter nor strict mode sees the `{}` a value may contain, and `LogEntry.isDbg()` marks it for `ConsoleLogger` (`DBG`, call site shown even without `showLocation`) and `JsonLogger` (`"dbg":true`).

`DbgSource` reads the text: the file is the package of the frame's class plus `getFileName()` (or the top-level class name when javac ran with `-g:lines`), looked up in `nanolog.sources` or in the roots derived from the class location (`DbgSource.LAYOUTS`, then `src/main/java` and the others under `user.dir`). A source newer than its `.class` is not trusted. `argumentsOnLine` requires exactly one `dbg(` call on the reported line, outside literals and comments, and scans at most `MAX_LINES` following lines for the closing parenthesis; the tokenizer (`tokenEnd`, `literalEnd`) knows strings, chars, text blocks and both comment forms, and the same tokens drive `splitArguments`. Every failure, I/O and invalid paths included, gives `null`, and the result, `null` too, is cached per call site in `DbgSource.CACHE`; `DbgSource.clearCache()` is for tests. `DbgTest` reads its own source, so changing the layout of a call in it changes the expected text.

`Dump` renders values for `Dbg.render` (`Dump.dump`) and, with `nanolog.dump=auto` (`Dump.auto`, read by `LOG.init()` through `DefaultLoggerCreator.readDumpAuto`), for `LogEntry.argToString` (`Dump.argument`). `Dump.kindOf` classifies a class once: arrays, then proxies and lambdas (`Proxy.isProxyClass`, `$$`, `$HibernateProxy$`), then collections, maps and `Optional` whose `toString()` comes from the JDK, then other JDK classes (`TEXT`, never reflected into), records (superclass named `java.lang.Record`, so detection works on Java 8 bytecode), classes with their own `toString()` (`TEXT`) and finally `FIELDS`. Kinds and field lists are cached in `ClassValue`s, which do not pin class loaders. `Dump.clearCache()` replaces them; a test that reaches `kindOf` or `fieldsOf` must call it in `@BeforeEach`, because pitest hot-swaps mutants into a running JVM and would otherwise see results computed by the unmutated code. The two styles share one walk: the dbg style quotes strings and applies `MAX_DEPTH`, `MAX_ITEMS`, `MAX_STRING` and redaction (`isSecret`); the argument style (`plain`) keeps the `toString()` of everything that has one, walks only JDK containers, without limits or redaction, and switches to the dbg style for the `undescribed` kinds (`FIELDS`, `NAMED`). Cycles are tracked by identity on the current path only, so a shared value is printed twice and is not a cycle. Every failure becomes `[FAILED dump()]`. Records cannot be compiled for Java 8, so `DumpTest` compiles one at run time and skips it below Java 16; on Java 8 the record branch is covered only through the mutants it shares with `FIELDS`.

`dbg` is temporary by design, and `Dbg` keeps track of the calls. Both `writeDbg` methods write through `LOG.writeDbgEntry`, which calls `Dbg.ran` with the frame: the call site (`Dbg.site`, `File.java:line`) goes into `Dbg.CALLS`, a synchronized `LinkedHashSet`, and the first call registers the shutdown hook `nanolog-dbg` through `Dbg.shutdownHooks` (a failure to register is swallowed), which prints the list with `Dbg.printCalls`. When the run summary (#62) lands, it takes the list over from the hook. `nanolog.dbg` (`Dbg.mode`, read by `LOG.init()` through `DefaultLoggerCreator.readDbgMode`): `OFF` is checked in `LOG.mayPrintDbg` before `mayBeEnabled`, so an off call walks no stack; with `FAIL`, `writeDbgEntry` reports the call through `LOG.diagnose`, which strict mode shares: `System.err` the first time a call site runs, `onDiagnostic` every time. A test that calls `dbg` must replace `Dbg.shutdownHooks` and call `Dbg.clearCalls()`, as `DbgTest` and `DbgLifecycleTest` do, or the test JVM prints the list when it exits.

`NanologChecks.assertNoDbgCalls` is a text scan, not a parser. It reuses `DbgSource.tokenEnd` and `isBlank`, so comments, strings, chars and text blocks are skipped exactly as when `dbg` reads its arguments, and it matches the token sequences `LOG . dbg`, `LOG :: dbg` and `LOG . name ( ... ) . dbg`. The example `examples/NoDbgCallsLeftTest` runs it on Nanolog's own `src/main/java`, so the library never ships a `dbg` call; Javadoc that shows `LOG.dbg` is fine.

### Caller auto-detection: `CallerDetection`

When the caller does not pass an explicit `Class`, `LOG.findCaller()` asks the locator in the package-private field `LOG.callerLocator` for the first stack frame outside Nanolog. Frames are skipped when their top-level enclosing class is `LOG`, `LogEntry`, `CallerDetection` (the locators themselves; a walk starts inside them) or an `ILogger` implementation (`CallerDetection.isNanolog`). The first remaining frame reaches loggers as `LogEntry.getCaller()` (the call site); the source class is that frame's top-level class (`CallerDetection.topLevel`). `getCaller()` is `null` for calls with an explicit class, which skip the walk. When no frame qualifies (a JVM run with `-XX:-StackTraceInThrowable`, or code running entirely inside an `ILogger` class), the locator returns `Caller.NONE` and the entry is logged without a source class and call site. **This filter is load-bearing**: any new intermediary class between user code and the actual logger must also be skipped there, otherwise it is misreported as the source class. The same holds if you ever add another public façade alongside `LOG`.

There are two locators, and `CallerDetection.best()` picks one when `LOG` initialises:

- `CallerDetection.StackWalk` (Java 9+): a `java.lang.StackWalker` with `RETAIN_CLASS_REFERENCE` that stops at the first qualifying frame and turns only that frame into a `StackTraceElement`. Nanolog is compiled for Java 8, so it reaches `StackWalker` through method handles found by name in its static initializer (a full `MethodHandles.lookup()`: `getInstance` is caller-sensitive and `publicLookup()` refuses it). On Java 8 that initializer fails, and `best()` falls back. Classes are never loaded by name, so a caller in a class loader nobody else can see is found exactly.
- `CallerDetection.ThrowableWalk`: the stack trace of a new `Throwable`, read through the package-private `ThrowableWalk.stackTraceOf` function (tests replace it to simulate an empty stack and must restore it). Frame classes are resolved by `resolveClass(...)`: the thread's context class loader first, then the loader of `LOG`, without initialization. A frame neither loader can see is skipped instead of aborting the call. "Cannot see" means any `Throwable` from `Class.forName`, not only `ClassNotFoundException`: a `LinkageError` from a child-first loader, GraalVM's `MissingReflectionRegistrationError` (an `Error`), a `SecurityException`. `VirtualMachineError` is caught as well, the same choice as `LogEntry.safeToString` and the guard around a lazy message's `Supplier`.

`best()` goes through `firstWorking(preferred, fallback)`, which takes the preferred locator only if it can be created and finds a caller once. `LOG.findCaller()` also catches anything a locator throws while logging and falls back to `ThrowableWalk`: a logging call never throws. Tests set `LOG.callerLocator` to exercise one locator in particular and restore it in `@AfterEach`. The class-loader tests in `LOGTest` (which compile a caller at runtime into an isolated `URLClassLoader`) pin `ThrowableWalk`, because resolving classes by name is its logic; `testStackWalkFindsACallerThatNoLoaderCanResolve` covers the walker. To count walks, wrap the locator in `CountingLocator`, which implements `ILogger` only so that its frames are skipped too. pitest cannot run `StackWalk` on Java 8: the `pitest-java8` profile in `pom.xml`, activated by the JDK, excludes it there; on every newer JDK it is mutated like the rest.

### Extension point: `ILogger`

Implementations: `ConsoleLogger` (default), `JsonLogger` (extends `ConsoleLogger`, overrides only `createLogString`; hand-written JSON escaping, one entry per line), `Slf4jLogger` (bridge to SLF4J), `MemoryLogger` (keeps entries for tests; `install()` / `close()` swap the logger of `LOG` and restore the previous one) and `CompositeLogger` (fan-out: enabled if any delegate is, each delegate receives only the levels it has enabled; a delegate that throws is reported through `LOG.reportLoggerFailure` and skipped, a throwing `isEnabled` counts as enabled). Custom loggers can be a lambda (`LOG.init(entry -> ...)`) because `ILogger` is effectively single-abstract-method. `isEnabled(level, sourceClass)` defaults to `true`; override it for level filtering. Run-time level changes go through the optional `ILevelControl` interface (`setLevel`, `clearLevel`, `resetLevels`, `withLevel`). Its abstract methods take the level as a string, parsed like `nanolog.level`, so `OFF` is expressible; the `LogEntryLevel` overloads are default methods that pass `Objects.toString(level, null)`, and `ConsoleLogger` / `CompositeLogger` override them only to return their own type for chaining. `ConsoleLogger` implements it, `CompositeLogger` forwards to its delegates that implement it (`withLevel` closes them in reverse order, so a delegate listed twice is restored correctly), and the static `LOG.setLevel(...)` family delegates to the installed logger. A logger without it is reported once per class through the `WITHOUT_LEVEL_CONTROL` set, which `LOG.clearReportedLoggerFailures()` also clears. Arguments are checked by the package-private `ConsoleLogger.isValidLevel` / `isValidName` / `isValidRule`, which `CompositeLogger` calls before forwarding, so a bad argument prints one diagnostic and not one per delegate. `mayBeEnabled(level)` also defaults to `true` and must never be `false` for a level that `isEnabled` accepts for some class, `null` included. `ConsoleLogger` and `CompositeLogger` implement it, and both answer `true` for a subclass that overrides `isEnabled` without `mayBeEnabled`. They detect such a subclass once in the constructor through `LoggerIntrospection.overridesIsEnabled`, which uses reflection and also answers `true` when the lookup fails, for example in a native image. It lives outside `LOG`, so creating a logger does not initialise `LOG`; initialising it inside a test would print its configuration diagnostics into that test's captured output. `LOG.log(...)` short-circuits on `isEnabled` before constructing the `LogEntry`, and `Supplier<Object>` messages are only resolved past that check, so lazy-message semantics depend on this order (`NoUnnecessaryCallsTest`, `MemoizingMessageTest`).

- `ConsoleLogger` reads its configuration in the no-arg constructor: `nanolog.level`, `nanolog.levels`, `nanolog.level.<package or class>` and `nanolog.console.*`. Setters called afterwards override what it read, but package and class rules are checked first in `isEnabled` and beat the five boolean switches. The rules live in an immutable `Rules` snapshot behind the `volatile` field `rules`: the thresholds by name, their lowest value, and a per-snapshot cache of thresholds resolved per `Class` (`findThreshold` walks from the class name outwards through `$` and `.`). Every rule change goes through the `synchronized` `replaceRule`, which copies the map, changes one name and swaps in a new snapshot; because the cache belongs to the snapshot, a thread that resolved a class against old rules cannot leave a stale entry in the new cache. The five switches are `volatile`; `setLevel(level)` and `resetLevels()` are `synchronized` so concurrent calls do not mix their switches. `RuntimeLevelsTest.testLevelStateIsSafelyPublished` asserts these modifiers, since pitest mutates neither. `mayBeEnabled` combines the lowest threshold of the current snapshot with the switches. One rule at `TRACE` therefore makes every `trace` call without a class walk the stack again. An invalid value goes through `DefaultLoggerCreator.printDiagnostic` and is ignored; configuration must never throw. `printDiagnostic` escapes control characters and U+2028/U+2029 as `\u000a`-style escapes, so a diagnostic is one line whatever it echoes (a level from a request, an exception message, a template); send new diagnostics through it, never straight to `System.err`.
- `ConsoleLogger` writes `ERROR` to `System.err`, everything else to `System.out`. Its single `SimpleDateFormat` is shared by all threads, so `writeDate` reads it once and formats inside `synchronized (format)`; keep that when touching the date code.
- `Slf4jLogger` caches one `org.slf4j.Logger` per source class in a `ConcurrentHashMap`. A `null` source class maps to the SLF4J `ROOT` logger (`ConcurrentHashMap` rejects `null` keys). An entry without a message is passed as an empty string, not `"null"`. The formatted message is passed as a plain string, so SLF4J never sees the `{}` arguments; markers are unsupported. When the SLF4J logger is a `LocationAwareLogger` (Logback, Log4j 2), `Slf4jLogger` calls its `log(marker, fqcn, ...)` with `LOG`'s class name as the caller boundary and `null` arguments, so the backend reports the code that called `LOG` and does not format the message again; keep every frame between user code and the logger inside `LOG` or skipped by the backend, or the boundary breaks. Tests use a package-private constructor that takes the logger factory, with `java.lang.reflect.Proxy` loggers, because only one SLF4J provider (slf4j-simple, not location-aware) can be bound in the test JVM.

### Bootstrap: `DefaultLoggerCreator`

On `LOG` class init (and on any `LOG.init()` with no args), a default `ILogger` is resolved as follows:

Settings are looked up by `DefaultLoggerCreator.getProperty(name)`: the system property first, then the environment variable of the same name in upper case with dots replaced by underscores (`nanolog.logger` → `NANOLOG_LOGGER`). Tests replace the package-private `DefaultLoggerCreator.environment` function instead of the real environment and must restore it in `@AfterEach`.

1. Load `nanolog.properties` from the classpath (or the resource named by `nanolog.config` / `NANOLOG_CONFIG`) through the thread's context class loader, falling back to the class's own loader when the context loader is `null`. Copy **only keys with the `nanolog.` prefix** (`DefaultLoggerCreator.PROPERTY_PREFIX`) into `System` properties, and only where neither a system property nor the environment variable is set, so the precedence is `-D`, environment, file, and the file cannot alter unrelated JVM settings.
2. If `nanolog.logger` (or `NANOLOG_LOGGER`) is set, `Class.forName(...).getConstructor().newInstance()` that class.
3. Otherwise, return `new ConsoleLogger()`.

Failures in step 2, and a missing file named by `nanolog.config`, are printed to `System.err` with a `[NANOLOG]` prefix and fall through to `ConsoleLogger`. An `IOException` while reading the file is rethrown as `RuntimeException` and would break `LOG`'s static initializer.

After loading the file, `loadPropertiesFromFile` hands the `nanolog.*` system properties, the environment variables and the keys of the file to `Settings.findings`, and prints one `[NANOLOG]` line per unknown setting (`reportUnknownSettings` swallows any failure). `Settings.KNOWN` is the one list of keys Nanolog reads, with the package rules `nanolog.level.<name>` on top; `SettingsTest` fails when a `PROPERTY_*` constant of `DefaultLoggerCreator` or `ConsoleLogger` is missing from it or from a settings table of the README, so a new setting needs all three. A system property whose value equals the file's is a key the file copied, and is reported with the file only. Unknown keys are reported under Nanolog's own namespaces (`console`, `exception`, `level` and keys without a dot); elsewhere, which is where a custom logger keeps its keys, only when `Settings.closest` finds a known key within one edit (names shorter than six characters) or two. Environment variable names come from `DefaultLoggerCreator.environmentNames`, values from `environment`; a test that controls the environment replaces both.

`createDefaultLogger` passes the configured logger through `RunLog.attach`, which returns it unchanged unless `nanolog.run=on`; then it returns a `CompositeLogger` of it and the `RunLog` of the JVM. `RunLog` is a `ConsoleLogger` subclass, so it reads the levels and is an `ILevelControl` like the console, and the composite routes each entry by the levels of each delegate; it is opened once per JVM (`RunLog.current`, `opened`; `RunLog.reset()` for tests), so repeated `LOG.init()` calls keep one file. Its constructor reads the console settings a second time, so `RunLog.open` builds it inside `DefaultLoggerCreator.quietly`, which mutes `printDiagnostic` on the current thread. `open` writes `runs/<id>.log` and `runs/<id>.errors.log` through unbuffered `Files.newOutputStream` streams, makes `latest.log` and `latest.errors.log` hard links to them through `RunLog.linker` (tests make it fail), and prunes `runs/` by file name, which starts with the time. `log` is synchronized: one line per entry to the run file and, for `WARN` and above, a one-line form (`brief` turns the stack trace into the exception's `toString()`) to the errors file; each stops at `maxSize` with a note, and an `IOException` closes both with one diagnostic. In agent mode it is on by default and leaves the path to the agent line; the run summary (#62) is meant to repeat it.

Agent mode (`nanolog.agent`, class `Agent`): `createDefaultLogger` calls `Agent.detect()` after loading the file, which returns what turned it on (`AI_AGENT=claude-code`, `nanolog.agent=on`) or `null`; detection reads the variables through `DefaultLoggerCreator.environment`, so tests control it. For a `ConsoleLogger` (or subclass) `Agent.shorten` calls the package-private `ConsoleLogger.useAgentDefaults()`, which sets `defaultThreshold` to `WARN` (also used by `resetLevels()`) and re-reads `nanolog.level`, `showDate` and `nanolog.exception.*` with the agent defaults inside `quietly`: a setting that is given wins, an invalid one gives the agent default, and the constructor has already reported it. Any other logger is left alone. `RunLog.attach(logger, agent)` defaults `nanolog.run` to `on` and does not print its own path line; `Agent.announce` prints the one agent line, once per JVM (`Agent.reset()` for tests). `LOG.init()` sets `Dbg.ignoreLevels` from a second, quiet detection: then `LOG.mayPrintDbg`, `LOG.printsDbg` (also for the `dbg` methods of `LOG.Limited`) and `CompositeLogger.log` let every `dbg` entry through whatever the levels.

Captures of one thread (`MemoryLogger.capture()`, `captureForwarding()`): `LOG.startCapture` adds the `MemoryLogger` to the copy-on-write list of the current thread in `LOG.CAPTURED` and increments `LOG.CAPTURES`; `endCapture`, called by `close()` from any thread through the list the capture keeps, removes it once. `LOG.captures()` reads `CAPTURES` first and the `ThreadLocal` only when it is not zero, so logging without a capture pays one volatile read. While the thread has a capture, the guarded `LOG.isEnabled` and `LOG.mayBeEnabled` answer `true` for every level; `write` then gives the entry to every capture of the thread and to the logger only if all of them forward and the logger itself accepts it (`LOG.accepts`, the former body of `isEnabled`), and `diagnose` follows the same rule for findings. Entries of other threads, pools included, are not captured; `LOG.wrap` (#26) is the place to carry a capture over. A capture keeps entries only from `keptFrom`, the logger installed when it opened (`null` for `captureForwarding()`), so a logger the test installs inside it still receives them; `everyLevel` is set for `capture()` and `captureForwarding()`, and `LOG.isEnabled` / `mayBeEnabled` answer `true` only for such a capture. `MemoryLogger.buffer()` is the capture of `NanologExtension`: it takes only the entries the logger accepts and holds them back from it.

`NanologExtension` (JUnit 5, compiled against the `provided` `junit-jupiter-api`) opens a buffer in `beforeEach`, closes it in `afterEach` and keeps it in the `ExtensionContext` store. `testFailed` writes the entries to `keptFrom` between two `--- log of ... ---` lines on `System.out` (unless `nanolog.junit.output=none`); `testSuccessful` and `testAborted`, and a failure with `none`, give them to `RunLog.replay`, which writes them to the run log only when `keptFrom` is a `CompositeLogger` that contains it. `nanolog.junit.output` is read once per JVM (`NanologExtension.reset()` for tests); with `all` no buffer is opened. `META-INF/services/org.junit.jupiter.api.extension.Extension` registers it when JUnit autodetection is on. `NanologExtensionTest` runs nested fixture classes through a `Launcher` of its own; the fixtures call `onlyThroughRun()`, an assumption, so any other runner, Surefire or pitest, skips them.

Run summary (`nanolog.summary`, class `Summary`): `LOG.init()` reads `Summary.mode` through `DefaultLoggerCreator.readSummaryMode(agent)` (`on` by default in agent mode, `off` otherwise) and, unless it is `OFF`, registers the shutdown hook `nanolog-summary` once per JVM through `Summary.registerHook` (`Summary.shutdownHooks` for tests). `LOG.write` calls `Summary.count` for every entry while the mode is not `OFF`: lock-free counters per level and per kind (level, call site or explicit class, template cut to `MAX_TEXT`), at most `MAX_KEPT` kinds, and the short trace of the first error with an exception, rendered once. `Summary.printOnce` prints the end of the run the first time it is called: the summary for `ON`, or for `ERRORS` after a `WARN` or `ERROR`, otherwise `Dbg.printCalls()`. Two callers race for it: the hook and `SummaryListener`, a JUnit Platform `TestExecutionListener` registered in `src/main/resources/META-INF/services` and compiled against the `provided` `junit-platform-launcher`. The listener is needed because Surefire drops the output of shutdown hooks in its forked JVM (measured with Surefire 3.2.5), which also hid the `dbg` list of #60. `Dbg.ran` registers the same hook, so a `dbg` call is listed at the end whatever the mode. Tests replace `Summary.shutdownHooks` and call `Summary.reset()`, which also forgets the `dbg` calls; `Summary.mode` is reset to `OFF` afterwards. Nanolog's own test JVM loads `SummaryListener` too, from `target/classes`; with the mode `OFF` and the calls reset it prints nothing.

The test JVM runs with `NANOLOG_AGENT=off` (`environmentVariables` of Surefire and pitest in `pom.xml`), so a build started by a coding agent behaves like CI; a test that needs agent mode replaces `DefaultLoggerCreator.environment` and `environmentNames` with a map, where the variable is absent.

Do not add a `nanolog.properties` to `src/test/resources`: it would be picked up by every test's `LOG` initialization. Tests use `nanolog.config` pointing at `test.properties` / `mixed.properties` / `levels.properties` instead, and clear every `nanolog.*` system property they or the file set.

### Stack traces: `ConsoleLogger.stackTraceOf`, `ShortStackTrace`

`ConsoleLogger.stackTraceOf` (also used for the `stackTrace` field of `JsonLogger`) returns the output of `printStackTrace` verbatim unless `exceptionExclude` or `exceptionMaxFrames` is set; only then does it use `ShortStackTrace`, Nanolog's own printer with the layout of `printStackTrace` (`Caused by:`, `Suppressed:` with indentation, `... N more` for frames shared with the enclosing trace, `[CIRCULAR REFERENCE: ...]` in the Java 9+ wording). Keeping the default on `printStackTrace` is what makes it byte-identical on every JDK and for throwables that override `printStackTrace`. `ShortStackTrace` lets every failure through and `stackTraceOf` falls back to `printStackTrace`, then to `[FAILED printStackTrace()]`. Because that fallback would hide a broken printer behind correct-looking output, `ShortStackTraceTest` tests `ShortStackTrace.of` directly; keep it that way when changing the printer.

### Message formatting: `LogEntry.formatMessage()`

Parameterized messages use `{}` placeholders (SLF4J-style). Escaping is non-trivial and has dedicated tests in `LogEntryTest`:

- `\{}` is a literal `{}`; the argument is **not consumed** (the consumer loop decrements `argIndex`).
- `\\{}` is a literal `\` followed by a substitution (both escapes consumed, the argument is substituted).
- Missing arguments leave `{}` in place; extra arguments are ignored.

Primitive arrays are rendered via `Arrays.toString`, object arrays via `Arrays.deepToString`; if `deepToString` throws because of an element's `toString()`, `arrayToString` falls back to rendering element by element so only the broken element becomes `"[FAILED toString()]"`. Every `toString()` call goes through `safeToString`, including those in `LogEntry.toString()`, and stack traces go through `ConsoleLogger.stackTraceOf`, which turns a throwing `printStackTrace` into `[FAILED printStackTrace()]`. Preserve this "logging never throws" guarantee when changing formatting code; the README promises it.

## Tests

- `AbstractLoggerTest` redirects `System.out` / `System.err` into buffers; `ConsoleLoggerTest` and `Slf4jLoggerTest` assert exact output lines (slf4j-simple is configured by `src/test/resources/simplelogger.properties`).
- `LOGTest` drives every overload and asserts the `LogEntry.toString()` representation; it also contains the class-loader scenarios.
- `DefaultLoggerCreatorTest` manipulates system properties and the context class loader and must clean up in `@AfterEach`.
- Classes under `src/test/java/com/nanolaba/logging/examples` are not tests: they are the README's code samples and only need to compile. The exception is `NoDbgCallsLeftTest`, the README's sample of a test, which runs.

## Dependencies

- `slf4j-api` is **`provided`**: required only if the consumer uses `Slf4jLogger`. Do not promote it to `compile` scope; that would force SLF4J onto every downstream user and defeat the "zero dependencies" claim in the README.
- `junit-jupiter-api` is **`provided`** as well: only `NanologExtension` uses it, in tests that have JUnit Jupiter anyway.
- `junit-platform-launcher` is **`provided`** for the same reason: only `SummaryListener` uses it, and only the JUnit Platform loads that class, in a test run that has the launcher anyway. Keep its version in step with `junit5.version`.
- `junit-jupiter`, `slf4j-simple`, `commons-lang3`, `pitest-junit5-plugin` are all test-scope.
- JMH (`jmh-core`, and `jmh-generator-annprocess` as an annotation processor) exists only in the `benchmark` profile, in test scope; see [Benchmarks](#benchmarks).
- The jar manifest declares `Automatic-Module-Name: com.nanolaba.nanolog` (configured on `maven-jar-plugin`); keep it stable, modular applications depend on it.

## Release build

The default build signs artifacts with GPG (`maven-gpg-plugin` 3.x, through gpg-agent) and publishes via `central-publishing-maven-plugin` with `autoPublish=true`. For local development use `mvn test` / `mvn compile` / `mvn verify -Dgpg.skip=true`; avoid `mvn deploy` unless you are actually cutting a release. Plugins are resolved from Maven Central only; do not reintroduce snapshot plugin repositories.

Release checklist:

1. Set the release version in `pom.xml` and the `nanolog.stableVersion` property to the same value, update the changelog section in `README.src.md`, run `mvn compile`, commit the regenerated README files, `llms.txt` and `SKILL.md` together with the sources.
2. `mvn clean deploy` (signs the artifacts and publishes them to Maven Central), then tag the release commit (`git tag -a vX.Y -m "Nanolog X.Y"`) and push the branch and the tag.
3. **Create a GitHub release for the tag.** Every published version must have one: `gh release create vX.Y --verify-tag --title "vX.Y" --notes-file notes.md`. The notes are the `### X.Y` changelog section from `README.src.md` (English), grouped into "New" / "Fixes" / "Documentation and build", followed by the Maven coordinates and a `compare/vPREV...vX.Y` link; the `v1.1` release is the reference layout. Do not publish it as a draft or pre-release.
4. Bump `pom.xml` to the next `-SNAPSHOT`, run `mvn compile`, commit the regenerated README files.

## Conventions

- Commit messages: English, imperative subject line, body explains the why.
- Keep the public API additive; this library is consumed from Maven Central.
- Every production change ships with tests that kill the corresponding pitest mutants and, where user-visible, with a README change in `README.src.md`.
- A killer feature (an issue labelled `killer-feature`) is not done until its SEO work is done too. Every such issue has an "SEO" section with the search phrases and a checklist; work through it. It covers a README section titled with the search phrase plus a "Why Nanolog" bullet (EN and RU), the GitHub description and topics (`gh repo edit`), `<description>` in `pom.xml`, the description in `agent-guide.src.md`, the first sentence of the Javadoc and the release notes. Claims stay honest: no keyword stuffing, comparisons with versions and dates. The baseline is issue #69.
